# src — React webview

React 19 + TanStack Router + [urql] (GraphQL) + Vite + Tailwind v4. UI primitives from `@kubetail/ui`. Package manager is **pnpm**. Path alias: **`@/*` → `src/*`**.

## Security invariants

The whole picture is [`docs/security-model.md`](../docs/security-model.md). What an ordinary change here can break:

- **Anything running in the webview holds the full cluster surface, and the shell behind it.** `graphql_query` forwards operations unexamined, so executing code can call every mutation, `approvalDecide` included. The CSP in `src-tauri/tauri.conf.json` is the containment — never widen `script-src`/`connect-src` to a remote origin, never load a script the bundle doesn't ship.
- **The approval request is the user's eye, and the eye is the whole gate.** `ApprovalRequest` (`chat-transcript.tsx`) draws exactly what will run — the command, path, content, edit strings, URL and host, memory name and body, or a cluster change's classified action, diff and request — with every invisible or reordering character spelled out (`VisibleText`) and long content folded behind a button Approve waits on. **Approve is a click on that drawn request and nothing else**: no keyboard shortcut, no default button, no approving from anywhere the request is not shown, no "always allow" for a raw command. Duration rules (*Allow for this command* / *this chat* / *Always allow*) are offered for a classified action alone, only where a grant can lift the verdict, armed as Approve is. A request whose action the UI cannot draw offers Deny alone. Adding any approval path is a security change → [the bash tool](../docs/security/2026-09-18-bash-tool.md), [the prompt names the action](../docs/security/2026-10-04-the-prompt-names-the-action.md).
  - **What runs unasked**: a command the sandbox confines; `Write`/`Edit` in the chat's workspace or a read-and-write granted folder; `Read` in a granted folder → [Bash runs in a sandbox](../docs/security/2026-09-28-bash-runs-in-a-sandbox.md), [path grants](../docs/security/2026-10-04-path-grants.md). A confined command wanting network the chat's switch and the turn's toggle don't give is its own request; the switch and toggle are the user's clicks alone, the switch behind a confirm (the composer draws no toggle yet, so a send carries it off) → [network is the user's switch](../docs/security/2026-10-04-network-is-the-users-switch.md).
  - **A grant is the user's act alone** (Settings, or `folderGrant`); a way for the model to make one is a security change.
  - Each cluster change a sandboxed command sends, and each read of Secret data, runs, asks or is refused per the context's mode and rules; Secret data passes `[redacted]` unless allowed → [cluster writes ask](../docs/security/2026-09-29-cluster-writes-ask.md), [the permissions engine](../docs/security/2026-10-02-the-permissions-engine.md), [Secret data is a permissioned read](../docs/security/2026-10-05-secret-data-is-a-permissioned-read.md).
  - A subagent's request is the same request, opening with *An agent asks:* and its `Agent` call's description → [the Agent tool](../docs/security/2026-09-25-agent-tool.md).
  - **Requests are drawn whether or not an answer streams, several at once, in the order asked**; buttons are live on a `Pending` approval while the message's `awaitingApproval` holds; **Approve arms only after its place on screen holds still for `APPROVE_ARM_MS` (500ms)**, re-arming on any move. The composer's *Show* and the chat list's dot point to a request and never approve one → [background agents](../docs/security/2026-09-25-background-agents.md).
- **The model's description of a command is its claim, never the app's.** One line, through `VisibleText`, italic and quoted, labelled *The model says:* on the request, never in place of the command and never brighter than it → [the command description](../docs/security/2026-09-23-the-command-description.md).
- **Cluster data is attacker-controlled text.** `src/` has no HTML sink — no `innerHTML`, `dangerouslySetInnerHTML` or `eval` — and `kstack/no-restricted-syntax`, `react/no-danger` and `no-restricted-imports` in `.oxlintrc.json` fail the lint on one, and on a template engine by import or call. Printer columns go through the restricted reader in `src/lib/jsonpath.ts`.
- **A chat answer inherits this.** `markdown.tsx` renders to React elements with raw HTML left as text; no rehype plugin may put HTML back.
- **The log viewer and the exec window inherit this.** Output is untrusted bytes: no HTML interpretation, terminal control sequences stripped. The sidecar strips each log line of every control but its SGR sequences (`services/logs`), and the viewer draws every cell through `VisibleText`, the message's colours through `AnsiText` (`components/widgets/ansi-text.tsx`: fancy-ansi's escaped output, parsed in an inert `DOMParser` document and read back as styled runs, never inserted). Copy writes a message without its sequences. The exec window, when it lands, brings both. → [log lines keep their colours](../docs/security/2026-10-19-log-lines-keep-their-colours.md).

## Routing & layout

- Entry: `src/main.tsx` → `RouterProvider`. Routes in `src/routes/` (code-based, wired in `src/routeTree.ts`): `__root.tsx` mounts the provider stack; `_app.tsx` is a pathless layout rendering `AppLayout`; `chat.tsx` (`/chat`), `chat-id.tsx` (`/chat/$chatId`) and `dashboard.tsx` nest under it. `index.tsx` redirects to `DEFAULT_ROUTE`. `_logs.tsx` is a second pathless layout, rendering `LogsWindowLayout`, with `logs-window.tsx` (`/logs`, the page every `logs-N` window loads) under it. **The chat id is a path param, not a search param** — `retainSearchParams` on `_app` would drag a search param into the dashboard. The Chat/Dashboard switch is the sidebar's `ModeNav` (router `Link`s).
- **Layouts** (`src/layouts/`) are presentational shells rendering an `Outlet`. `LogsWindowLayout` is the log window's: one column the window's height bounds, no sidebars, no dialogs host; its page draws its own bar.
- App-wide concerns live in `src/lib/`; reusable UI in `src/components/widgets/`.
- **`ReadyGate` (`src/lib/ready-gate.tsx`) draws `AppMark`** at 48px, centred, in every state. `AppMark` draws `src/assets/icons/`'s light or dark app icon, one per scheme; those are `make generate-icons`' copies of `src-icons/`. `index.html` carries a static copy of the same mark inside `#root`, so first paint and React's first commit show the same thing in the same place — keep them matching. It also draws a 48px `data-tauri-drag-region` strip over its top edge, so the window drags before the app bar mounts; `index.html`'s static copy carries the same strip.

## Errors reach the host's log

`reportError` (`src/lib/error-bus.ts`) is the one producer; `src/lib/error-log.ts` is the sink: `startErrorLogForwarder` sends each record to the host's `webview_record_error`, and `installGlobalErrorHandlers` reports `error`/`unhandledrejection` as `render`. Both are called in `main.tsx` **before `createRoot`**. A module that throws while loading is not covered. **`errorReportExchange` forwards every GraphQL operation error**, so a component never calls `reportError` for one.

- An `AppError`'s `context` holds **explicitly chosen keys, never a serialized `cause`** — a `CombinedError` holds GraphQL payloads full of cluster text.
- The forwarder reads each field under its own guard (a getter can throw), caps strings, swallows a rejected invoke, and **never calls `reportError` on failure** (that would loop).
- Sends past `MAX_IN_FLIGHT` are dropped, `RESERVED_IN_FLIGHT` slots kept for `render`/`auth`; the drop count rides as `context.dropped` on the next record.
- The host is the authority on caps and rate limits (`src-tauri/CLAUDE.md`, Logging).

## Window-scoped state = URL search params

`kubeContext`, `resource`, `namespace` and `chat` are search params on `_app`, kept across mode switches via `retainSearchParams` — per-window, deep-linkable, history-pushing. → [ADR: URL params as window state](../docs/adr/2026-08-09-url-params-as-window-state.md). Accessors: `useActiveKubeContext` (`src/lib/active-kube-context.tsx`; falls back to the kubeconfig current context; `setContext` writes the param and never rewrites the kubeconfig) and `resolveDashboardResource`. `chat` is the dashboard panel's open chat, read by `DashboardChat` alone. `namespace` is the dashboard's namespace scope, absent for every namespace, read and written through `useNamespaceScope` (`src/lib/namespace-scope.ts`); only the dashboard reads it, and the omnibox's cluster switch clears it with `chat`. **The cluster is the window's one high-level scope**; everything else follows from it. → [ADR: the cluster is the app's scope](../docs/adr/2026-09-11-the-cluster-is-the-apps-scope.md), [ADR: the dashboard's namespace scope is a search param](../docs/adr/2026-11-12-the-namespace-scope-is-a-search-param.md). **Links writing one param must spread the previous search** (`(prev) => ({ ...prev, resource })`).

**Window layout** (`layouts/app-layout.tsx`, the one place the shape is expressed): a 48px app bar over a row of the left sidebar, `<main>` and the right sidebar. Nothing is fixed-positioned. Traps:

- **The app bar** (`app-bar.tsx`) is a `deep` Tauri drag region; controls inside stay clickable via Tauri's hit test, and the omnibox opts out with `data-tauri-drag-region="false"`. A press that drags never reaches the webview as a click, and Base UI's popovers dismiss on an outside click, so the bar's `onPointerDown` (`dismissPopupsOnWindowDrag`, `src/lib/window-drag.ts`) clicks the pressed element itself. `startsWindowDrag` there mirrors Tauri's drag hit test; diff it against `drag.js` on a Tauri upgrade. On macOS it reserves the native traffic lights (`window_manager.rs` mirrors the 48px); elsewhere it mounts `AppMenu` and `WindowControls`. **Only the two bars check the platform** (this one and `logs-window-bar.tsx`) — not mounting `AppMenu` on macOS keeps its `Ctrl/Cmd+N`/`Q` from firing beside the native menu's. Every bar control is drawn through `app-bar-button.tsx` (`AppBarButton`, `AppBarGroup`/`AppBarDivider`, and `TrafficLightGutter`, which the log window's bar shares); bar tokens are `--app-bar*` in `index.css`. The bar has no padding, so the close button reaches the corner.
- **`open_account_url` names the URL itself** — a host command that opened whatever the webview handed it would be an exfiltration channel.
- **The left sidebar** (`left-sidebar.tsx`): the library's `SidebarProvider` owns `Cmd/Ctrl+B`; open/collapsed is controlled from the layout via `usePersistedFlag`, since the library's `sidebar_state` cookie is never read back. Open is `LeftSidebarCard` (drag-resizable), collapsed is `LeftSidebarPill` in the same footprint. **Narrowness is the provider's own `isMobile`, never a second media query** — `toggleSidebar` branches on it to flip `open` or `openMobile`, so a component using another rule flips a state nothing shows. Narrow, the toggle opens the card as a drawer over the content row (`relative` in `app-layout.tsx`); a scrim, Escape or any navigation closes it.
- **The drawer is `role="dialog" aria-modal`, held by `useFocusTrap`** (`src/lib/focus-trap.ts`). Both yield to an overlay opened inside it: the trap stands aside while its node sits under an `aria-hidden="true"` element, and the drawer's Escape listener is on `window`, after the `document` listener a dialog dismisses on, so one keypress closes the dialog alone.
- **The right sidebar** (`right-sidebar.tsx`) is a row item, taking width from the page. It has no fixed maximum: a drag stops where `<main>` reaches its floor, `min(320px, 50%)` of the row (`PAGE_MIN_WIDTH`). On a narrower window it shrinks to its minimum before `<main>` goes under that floor, leaving the stored width alone. `ResizeHandle` and `usePersistedWidth` (`src/lib/persisted-width.ts`) are shared with the left card. `RightSidebarToggle` is pinned to the content row's top-right corner, below the left drawer's scrim. Its state is `useRightSidebar` (`src/lib/right-sidebar.tsx`) — chrome, out of the URL, persisted **per mode** (open state and width); the layout supplies the mode, and `usePersistedWidth` re-reads when its key changes. **The `aside` does not scroll**; its contents own a scroller each.
- **The right sidebar's content**: on the dashboard the focused object (`ObjectPanel`), else `DashboardChat`; in chat mode the focused log view (`logs-view-panel.tsx`) or a placeholder. **The focused view is `useLogsView`** (`src/lib/logs-view.tsx`): `{ clusterId, chatId, callId, action, grep? } | null`, chrome, not persisted; `grep` is the user's from the viewer's toolbar, kept while the same call stays focused, so it survives the panel unmounting while the sidebar is collapsed. `set` also opens the right sidebar, so `LogsViewProvider` mounts inside `RightSidebarProvider`. The panel's close collapses the sidebar and leaves the view focused, like the toggle; a cluster switch from the picker clears it, and so does moving it to a log window. A view opens on a transcript card's button alone, Expand (`logs-view-card.tsx`) or *View around this* (`logs-read-card.tsx`, `logs-watch-card.tsx`), never by itself. `viewOfCall` (`logs-view.tsx`) is the call → view mapping those buttons make.
- **A view moves to a log window** on *Open in window*, on the panel's header or beside a card's button. A view is in one place at a time: `logs-view-buttons.tsx` decides each card's (`useViewPlace`: a log window, then the sidebar while it is open and focused on the call, else the card), and the card hands it to `LogsViewButtons`, which draws: *Showing in a window* with *Show window*, *Showing in the sidebar*, or the card's button and *Open in window*. Only a LogsView card hides its inline lines while the view is elsewhere. **`LogWindowsProvider`** (`src/lib/log-windows.tsx`, under `LogsViewProvider` in `AppLayout`) is the app window's side of the host's pair (`src-tauri/CLAUDE.md`, *Log windows*): it subscribes once per mount, each subscribe with a channel of its own (Tauri ends a channel when the host drops the side a subscribe handed it, which a later subscribe does), all folding through one handler, keeps the **largest page** any subscribe answers (two can land in either order), folds `snapshot`/`opened`/`closed`/`focused` into a map by label, and navigates on `showChat`. **Each window's viewport is a mirror kept out of React state** (`createMirror`, `src/lib/log-window-push.ts`): made when a `snapshot` or `opened` first names the window, folded from every push those frames and `viewport` frames carry, never replaced while the window lives, and dropped on `closed` or a `snapshot` without it. A `viewport` frame re-renders only what reads the mirror. A mirror keeps its selection array while the push's generation and `selectionRevision` hold. `shownWindowOf(chatId)` is the chat's window with the highest `focusSeq`, with its mirror. It is `ready` once the page and the cluster are known; the window buttons are disabled until then. **Opens and closes go through one queue**, each after the last settles, since the host's open is async and its close is not. An open carries the focused view's grep when it is the same call, is dropped at its turn if its view is not on the held cluster, and on success clears the focused view if it is still that call, closing the sidebar if it showed it. **The held cluster** is the last defined `clusterID` since the page; the first is held with no close, and a later different one queues `log_window_close_all`. The windows are checked against the held cluster once per snapshot and once per page, and a window on another cluster queues a close too. An undefined `clusterID` changes nothing.
- **The log window's page** (`components/widgets/logs-window.tsx`) asks the host `log_window_view` once per mount (a refusal draws *This log window could not load.* with *Try again*), then reads the chat, its messages and the clusters. It draws *Loading…* until all three bookmarks (a reconnect masks a watch's data until its new bookmark, so the view drawn before it stays mounted through that, keeping the viewer's grep, scroll and selection), *This chat was deleted.* or *This log view is not available.*, else the panel's header (`LogsViewHeader`, no buttons) over `LogViewer` with a viewport of its own. The grep is the user's from this window, else the open's, else the action's. It sends `log_window_title` with the first source, the chat's title and the cluster's name, an empty part for one missing. **It pushes its viewport** (`createViewportPublisher`, `src/lib/log-window-push.ts`) through `log_window_viewport`, stamped with the answer's `generation` and the grep in effect (applied here, else the open's, else the action's), which the host keeps, so a reload keeps the toolbar's grep. The handle, the applied grep and the publisher live in `Paired`, above the viewer a notice unmounts. A push carries whole selected lines, at most 50 within 192 KiB of UTF-8 (`cutSelection`), the whole `selectedCount`, and a `selectionRevision` that steps on each new selection array. One is in flight at a time; a change to the selection, the count or the grep goes on the next frame, the rest after 250 ms, and `blur` sends at once. A refused push is reported and not resent. `LogsWindowBar` is its 40px drag bar: the cluster's dot and name and the chat's title through `VisibleText`, *Show chat*, the traffic-light gutter on macOS and `WindowControls` elsewhere, with no `AppMenu`.
- **The log viewer** is `components/widgets/log-viewer/`; its `index.ts` exports `LogViewer`, plus `LOG_ROW_PX`, `CutNotice`, `Dot`, `GapNotice` and `lineTime` for the transcript's cards, and nothing outside imports a part. It builds its client once per mount through **`createLogsClient(urql, clusterId, action)`** (`src/lib/logs-client.ts`, the one place the app makes a `Client`: `logsFetch` with `requestPolicy: 'network-only'`, since a page's variables repeat; `At` as two disjoint pages joined, the older ending the nanosecond before the moment; `Until` and `Since` as one first page each, the bound as given, with `seen`; `logsFollow` from a page's cursor, a reconnect sending the `seen` given and the newest line it handed on of each container, an `Ended` unsubscribing, a follow the sidecar could not open calling `onFailed`) in a `useState` initializer. Cursors pass through as the sidecar wrote them. `scopeInput` builds the `LogsScopeInput` field by field, since the action carries `__typename`s. It lands at the action's `openAt` on mount only. **The toolbar's grep box replaces the action's grep** for the focused view. A submitted pattern is checked with a one-line read through a client built with it, since the sidecar compiles a grep before it reads. Accepted, the viewer swaps to that client, lands at the end while pinned and else at the first line on screen, and reports it through `onGrepApplied` and the viewport's `grep`, so the panel's header and the chat's snapshot name the grep in effect. Refused, the reason shows at the box and the view stays. Cells are drawn through `VisibleText`, the message through `AnsiText`; the dot colour is inline (no CSS name built from cluster text). A cut line ends with `CutNotice`, its `truncatedBytes` in KiB. The notices of the window's pages and follow draw over the lines, `code` in a `title`. A line's `gap` draws a notice above it in the same row (one more `LOG_ROW_PX` in `estimateRowHeight`), its names through `VisibleText`; selection passes over it and a row's copy writes it in brackets. Selection is kubetail's, ported (`selection.ts`); keys go on the scroller, never `document`, so a page can hold two viewers. Enter/Space on a cell are taken in the capture phase, before the scroller's intent reader would read Space as scroll-to-bottom. Copy goes through `navigator.clipboard.writeText`, a refusal to `reportError` as `render`. A failed page or follow is drawn, not reported: `errorReportExchange` has reported it. It writes what is on screen to the window's one **`LogViewportHandle`** (`src/lib/log-viewport.ts`), and the empty viewport on unmount. Columns and wrap persist as `kstack:log-viewer-columns` / `kstack:log-viewer-wrap`. See the directory's files for rows, header, toolbar, jump-to-time and wrap.

The **context omnibox** (`context-omnibox.tsx`) sits in the app bar's centre: the **`StatusButton`**, one trigger and the **`MemoryButton`**. The pill has no padding of its own, so a press anywhere but the two icon buttons lands on the trigger and opens **`ClusterPicker`** (`components/widgets/cluster-picker/`, exporting the picker alone). The picker hangs from the omnibox and lists the kubeconfig's contexts, the window's first, each with `src/lib/cluster-health.ts`'s verdict (`contextHealth`: the Clusters dialog's own, *Not reached* without a record or before the clusters `Bookmark`); a filter appears from six contexts. It hangs below the server icon, left edges aligned, 320px wide and as tall as its content, scrolling the alerts and sections between a fixed header and footer when the window is shorter, so a long message never hides the footer's buttons; it neither resizes nor remembers a size. With no kubeconfig context there is no status button, and the trigger draws the bare icon. ## Dashboard resource nav

`DashboardResourceNav` (`components/widgets/dashboard-resource-nav/`, exporting the nav alone) draws the namespace picker (`NamespacePicker`), the pinned Overview and Events rows (`NavItem`), a rule, a sticky search box, then a *Cluster* and a *Namespace* section (`SectionHeading`) of groups (`NavGroup`) of kinds. The rule is the card's only one, so the search box reads as heading the sections it filters. `buildDashboardNav(kinds)` (`src/lib/dashboard-resources.ts`) places each kind: **its scope is its section**; its group is the curated kind's (`GROUPS`), else its API group's (`API_GROUP_TO_GROUP`), else a core plural's (`CORE_KIND_TO_GROUP`), else *Custom resources* for a CRD and *Extensions* for the rest. A curated kind matches on API group **and** plural, so a CRD reusing a built-in's plural never takes its row. A curated or core kind's id is its plural, any other's `<group>/<resource>`; Events are the pinned row, never a section's kind. **Before the catalog's `Bookmark` (`useDashboardNav` gates on it) the tree is the curated kinds without counts and nothing hides.** After it, `filterNav` hides kinds with no objects, the current kind excepted; a search reaches them; a search is a case-insensitive prefix match on kind labels that holds every group open. Group rows only open and close; a closed group holding the current kind draws as selected (`SELECTED`, shared with `NavItem`). Each group's open state is a `usePersistedFlag` (`dashboard-nav-open:<section>/<group>`); with nothing stored, each section's first group starts open and the rest closed; moving to a kind opens its group. A section heading is a label, not a toggle; the picker above names the namespace scope, so the *Namespace* heading does not. Kind labels draw through `VisibleText`. `DashboardResource` is an **open string**, validated leniently. → [ADR: dashboard nav merge](../docs/adr/2026-08-09-dashboard-nav-merge.md), [ADR: the dashboard nav groups kinds by scope and API group](../docs/adr/2026-11-12-the-dashboard-nav-groups-kinds-by-scope-and-api-group.md).

Live data: `ClusterCachedDataKindsProvider` (`src/lib/cluster-cached-data-kinds.tsx`) holds the window's **one** `clusterCachedDataKindsWatch(id, cacheID, namespace)` subscription, **subscribed with the namespace scope**: each namespaced kind's count (and Events') is the namespace's, a cluster-scoped kind's the whole cache's, and the frame's echoed `namespace` joins `cacheID` in its provenance, so a namespace switch re-subscribes like a cache swap; `AppLayout` mounts it above the sidebar and the routes, enabled only on the dashboard, so the catalog outlives the nav's card and a reopened nav reads it whole. `useClusterCachedDataKinds` reads it; `useDashboardNav` builds the tree over it. All three cached-data hooks resolve the cluster/cache through `useActiveCluster()` (`src/lib/active-cluster.tsx`) and reduce through **`useCacheDeltaWatch`** (`src/lib/graphql/use-cache-delta-watch.ts`), which owns the id-keyed fold, `watchPhase`, and the **cache/kind provenance guard** (rejects rows from a superseded cache — don't bypass it; → delta-watch ADR). `AppLayout` mounts `DashboardResourceNav` only while `/dashboard` matches, and `ClusterNamespacesProvider` (`src/lib/cluster-namespaces.tsx`) beside the catalog's provider, enabled the same way: the window's one `v1/namespaces` watch, `unshared`, since a Namespaces page watches the same kind and the later of two shared consumers never sees the snapshot.

**The namespace picker** is the nav's first row: a `ScopeMenu` behind a `ScopeTrigger` (`dashboard-resource-nav/scope-menu.tsx`), a combobox search box over a listbox of options under labels; the caller's `entries(query)` decides what matches; the arrows move the highlight over options from the box, Enter picks, and it opens scrolled to the current option. Its menu is *All namespaces*, then the namespaces matching a substring, the chosen one kept (*Not found* once the list has landed without it).

**A dashboard page is `PageHeader`** (`components/widgets/page-frame/page-header.tsx`) **over its panel**, with no toolbar. `routes/dashboard.tsx` picks a page from `resource`: `events` → `EventsPage` (`useClusterCachedDataEvents`, then `EventsTable`); a resolved discovered kind → `KindPage` (`useClusterCachedDataObjects(kind)`, keyed by cache **plus** `apiVersion`+`resource`, then `ObjectsTable`), held through a reconnect's replay of the catalog so the table stays mounted. **A page owns its watch and filters it by the namespace scope**; a cluster-scoped kind is not filtered and says so under a namespace. Events' header counts its rows, drawn only after the watch's `Bookmark`. **A kind page's header is its label alone.** Anything else is `PlaceholderPage`: a resource `mayNameDiscoveredKind` accepts (anything but Overview) but the catalog lacks reads "not synced" with no active cache, a spinner before the Bookmark, and "not served" after it; Overview reads "coming soon". The title is `dashboardResourceLabel`'s. `rawJSON` is the full native body (`unknown`). Both tables take their rows, `active` and `phase` as props and gate on them: no active cache → "not synced", `connecting` → spinner, `live` with no rows → "No …" (naming the namespace under a scope, where `ObjectsTable` also drops its Namespace column).

**A kind's columns come from `components/widgets/object-columns/`**, which exports `columnsForKind`, `toneForKind`, `Age` and `ageSortValue`:

- **A hand-written entry wins**, else the kind's `printerColumns` evaluated by `src/lib/jsonpath.ts`. Those kubectl prints only under `-o wide` (`priority > 0`) are `hiddenByDefault`. A printer column's value truncates to its column, like a built-in text column's. Its key is its name (`printer:<name>`), not its place, so a user's choices for it hold when the CRD adds or moves another.
- **Every built-in kind is hand-written**, one file per nav group (`pods.tsx`, `workloads.tsx`, `cluster.tsx`, `dra.tsx` for dynamic resource allocation, `network.tsx`, `config.tsx`, `storage.tsx`, `access.tsx`, `extensions.tsx`); `registry.tsx` joins them by `gvrKey`. Each draws kubectl's columns; its `-o wide` columns and more of the object's fields are `hiddenByDefault`.
- **A kind's entry is `kind<Body>(apiVersion, resource, columns)`** (`common.tsx`). `Body` is the narrow shape the kind reads off `rawJSON`, named once. Each column is a builder (`textColumn`, `listColumn`, `countColumn`, `quantityColumn`, `readyColumn`, `ageColumn`, `durationColumn`, `statusColumn`) over a reader of that body, or a `KindColumn` written out where none fits.
- **A status column gives the kind its tone.** `statusColumn`'s reader returns the label and tone of its `StatusPill` (`components/widgets/status-pill.tsx`), and `toneForKind` reads the tone off that column, so the tabs and the pill cannot disagree. The pill carries its whole label as its `title`. A PersistentVolume or claim being deleted reads *Terminating*, whatever its phase. A tone is drawn in cluster health's palette: `HEALTH_TONE` maps it onto `TONE` (green, amber, red). A Deployment's status is `kubectl rollout status`'s reading. Until the current generation is observed it is *Progressing*, whatever an earlier rollout's conditions say. It is *Available* once every desired replica is updated, no old one is left, and every updated one is available.
- **A cell is redrawn only on a new frame**, so one that reads the clock ticks itself: `Age` through `react-timeago`, a running Job's Duration through `Elapsed` (`workloads.tsx`), which stops once the Job has a `completionTime`. A column whose sort value reads the clock says so (`sortsByClock`), and the table sorts by it again each second.
- **A pod's tone is its status's (`podStatusTone`), except that a running pod is `pending` until its Ready condition holds**, so a starting pod never reads failing and a never-ready one never reads healthy. Its columns are Status, Ready, Restarts (destructive above zero) and Node.

**`ObjectsTable` draws a kind's rows in the mockup's card**: a muted header row, cells tighter than the library's (12px between columns), and a *Showing N of M* footer.

- **Rows are two lines tall** (`TALL_ROW`), their cells without vertical padding: a row's height is only a minimum, and two lines under the library's padding would outgrow the height the table's arithmetic assumes. Name is the name over its owning workload (`ownerOf`, `src/lib/object-owner.ts`: the controller owner, a Deployment's ReplicaSet read as the Deployment by its `pod-template-hash`). Age is as kubectl prints it (*22m*, *3d*).
- **A kind with a tone gets status tabs above the table**: *All · Healthy · Failing · Pending*, with counts over the scope's rows, each count above zero in its tone's colour. A tab filters the rows, and the footer counts what it shows. A tab or a filter that leaves no row draws the table empty (*Showing 0 of N*).
- **A text filter sits under the tabs, just over the table**: a `SearchBox` that Escape clears. `matchesFilter` (`src/lib/object-filter.ts`) matches a case-insensitive substring of the name, the owner as drawn, a label as `key=value`, the node, or the namespace while its column shows. A custom resource can hold anything at `spec.nodeName`, so only a string there is matched. It narrows the rows before the tabs count them.
- **A column picker sits at the filter's right** (`ColumnPicker`, `components/widgets/column-picker.tsx`): every column in the table's order, each with a checkbox, Name's locked on, and a handle that drags it to another place or moves it from the keyboard. *Reset* returns to the defaults. The popup is no taller than the room it has, and its list scrolls. The handle goes through dnd-kit's pointer and keyboard sensors, never HTML drag and drop, which Tauri's file drop swallows on Windows.
- **`useTableColumns` (`src/lib/table-columns.ts`) keeps the user's choices and order per kind in localStorage**, each against the column's default, so a column the table gains later takes its own default place and visibility (`arrange`). A `hiddenByDefault` column waits to be picked, as Pods' IP, Host IP, Containers, Images, QoS class, Service account, Priority class, Controlled by and Started do.
- **A column with a `sortValue` sorts.** Its header is a button with two muted triangles, the sorted direction lit. The first press sorts it (largest first for a `descFirst` count), the next reverses it, the next returns to the watch's order. `sortRows` (`src/lib/sort-rows.ts`) is stable and puts a missing value last. The sort is the table's own state, reset by keying the table on its kind, and the footer names it (*Sorted by restarts*).
- **The last column is the row's actions** (`actionsColumn`, `components/widgets/object-actions.tsx`): a ⋯ button on every row, under no header, outside the column picker and its order. Its menu is *View YAML* and *View events* for every kind, and *View logs* for the kinds of `LogsViewSourceKind` (`logsSourceKind` maps a `gvrKey` onto one, so a CRD reusing a built-in's kind name is not one). Each item goes to the table's `onAction` with the row, which `KindPage` (`routes/dashboard.tsx`) answers by focusing the object on that tab.

**The focused object is `useObjectView`** (`src/lib/object-view.tsx`): the object's kind, `uid`, namespace and name, or null, and its open tab (`yaml`, `events` or `logs`). It is chrome, like the focused log view: out of the URL, so Back and Forward leave it alone, and not persisted. `set` opens the right sidebar. The object is bound to the cluster it was focused in: `ObjectViewProvider` drops it once the active cluster is another, however the window got there (the picker, Back, a new default context). `ObjectPanel` (`object-panel.tsx`, keyed on the uid) draws a header naming the object, with Close, over its tabs, mounting the open tab alone. Close clears the object and the chat comes back.

- **YAML** (`object-yaml-view.tsx`): `objectYaml` (`src/lib/object-yaml.ts`, the `yaml` package) prints the body kubectl's way, highlighted by `highlight.ts` with every text run through `VisibleText`, with Copy. The last body seen is held through a reconnect and, once the object is gone after a `Bookmark`, marked *Deleted*.
- **Events** (`object-events-view.tsx`): the cache's Kubernetes Events whose involved kind, namespace and name are the object's, newest first. Each draws its type (`TypeBadge`, from `events-table.tsx`), reason, count, age and wrapped message, through `VisibleText`.
- **Logs** (`object-logs-view.tsx`), for a log kind alone: `LogViewer` over a `LogsViewAction` the tab builds, with no chat behind it. The object is its one source (a workload reads its pods), every container, landing at the tail and pinned. The grep the toolbar applies lasts the mount, and its viewport handle goes unread: the dashboard chat sends no snapshot.
- **YAML and Events each hold an `unshared` watch of their own**, so they stay live whatever page the window shows. A second shared consumer of a running watch would never see its snapshot.

**Both tables render through `VirtualTable`** (`components/widgets/virtual-table.tsx`), only the on-screen rows in the DOM between two spacer rows. These hold it up:

- **Every row of a table is one height, `ROW_H` unless the table passes a `rowSize` (`TALL_ROW`), and the pixels are read off a rendered row** (`TableRow`'s `border-b` under collapsed borders makes it not `h-9` arithmetic). A wrong constant drifts rows further down a long list.
- **The table is `table-fixed`**: widths come from a `<colgroup>` the header's table and the body's share (the body's first row is a spacer with no cells), each column's `width` in pixels (`object-columns/` sizes every kind column); free-text columns `truncate` with a `title`. The one unsized column (Name, an event's Message) takes the slack and keeps its `minWidth`: the table's minimum width is the sum, so a narrow page scrolls sideways rather than squeezing that column to nothing. `ObjectColumn` is a `VirtualColumn` whose `width` is required.
- **The header is a table of its own above the scroller**, so the scrollbar starts under it. It pads its right edge by the scroller's bar (`offsetWidth − clientWidth`), so its columns stay over the rows'. It follows the scroller's `scrollLeft` by a `translateX`, never by scrolling itself: WebKit leaves that padding out of a box's scroll range, so a scrolled header would stop short at the far right.
- **The two tables read as one.** The wrapper is `role="table"`, both native tables are `role="none"`, and their sections, rows, headers and cells name their own roles, so a screen reader ties each cell to its column's header.
- **The scroller's bar is `table-scrollbar`** (`index.css`). Styling WebKit's bar makes it a classic one beside the rows, so their borders never show through a macOS overlay bar. It sets only the `-webkit-` pseudo-elements: Chromium drops them once `scrollbar-width` or `scrollbar-color` is set.

**The table corrects its own scroll**: after each commit it moves `scrollTop` by the *smallest* shift any surviving on-screen row made, doing nothing within one row of the top; the scroller sets `overflow-anchor: none`. The window is clamped to the rows there are, so a list a filter or a tab cuts short under a deep scroll still draws its rows. → [ADR: the virtual table owns its scroll anchoring](../docs/adr/2026-10-17-the-virtual-table-owns-its-scroll-anchoring.md). The scroller is `tabIndex={0}` for Home/End/PageUp/PageDown.

**The layout bounds the scroll, and the window never scrolls.** `html` is `overflow: clip` (`index.css`), so a wheel outside every scroller moves nothing. The chain is `h-(--app-min-h) min-h-0` on the `SidebarProvider` column, `min-h-0 flex-1 overflow-clip` on the content row (its items' minimum widths can outgrow a narrow window), `min-h-0 flex-1 overflow-hidden` on `<main>` (all in `app-layout.tsx`), `flex min-h-0 flex-1 flex-col` on the route's `<section>`, then the table's `flex-1 overflow-auto`. Traps:

- `min-h-0` goes on every *plain* flex item between frame and scroller, never on the scroller itself.
- It must stay beside `h-` on the provider: only `min-h-*` displaces the library's hardcoded `min-h-svh` via tailwind-merge, and on Linux `--app-min-h` (100% of the `WindowFrame` inset) is shorter than `100svh`.
- That percentage is definite only while every DOM ancestor is — one wrapper `<div>` between `WindowFrame` and the provider breaks it.
- Any other scrolling route under `_app` needs `min-h-0` on its own chain (`chat.tsx` via `CenteredColumn`).
- Tests that render rows call `stubLayout()` from `@/test-utils`; jsdom has no layout, so a virtualized table renders none.

## Chat

**Panes.** `chat-pane.tsx` holds `ChatPane` (one chat: transcript over composer) and `NewChatPane` (a chat not yet started: its `empty` slot over a composer). Chat mode's page and the dashboard's right sidebar mount them. Neither navigates: they report `onCreated(id)` / `onGone()`, and the home decides — `chat.tsx` goes to `/chat/$chatId` with `replace: true`, `chat-id.tsx` back to `/chat`, `DashboardChat` writes or clears its `chat` param. → [ADR: the answer is a record](../docs/adr/2026-09-10-the-answer-is-a-record.md).

**Reads are `src/lib/chats.tsx`.** `useChats` sorts by `Date.parse(updatedAt)` desc then `id` desc (millis tie). `useChatMessages(chatId)` orders by `seq`; ids order nothing. Both are `unshared: true`, fold an id-keyed map over `useWatchSubscription` (no `useCacheDeltaWatch`: no cache provenance), and gate on `type === 'Bookmark'`. The file holds the one reader of each part of a message — keep it that way, since a second, laxer narrowing of `content: JSON!` is how a tool block reaches the screen:

- `textOf` — text blocks only. Tool rounds, thinking, `context` and notice blocks draw nothing; a `tool_use`/`tool_result` round or a `server_use` block between two text blocks becomes a blank line.
- `contextOf` (a question's cluster card), `noticesOf` (background-task notices), `searchesOf(toolCalls)` (the answer's own `Search` calls that `ranSearch` passes, queries off `action.search`), `sourcesOf(citations)` (one entry per URL, citing order). Web text is data, drawn as text.
- `summaryOf`, `toolCallTag`, `grantOffered`, `waitingRequestsOf`, `inFlight` — see below.
- `chatModeOf` is the one `AppMode` → wire mapping, so the list filter and the send agree.

**A chat belongs to one mode and one cluster** (`Chat.mode`, `Chat.clusterID`, fixed at creation). The list watch is unscoped and both filters are the client's, since `OpenChat` must tell a deleted chat from another cluster's. **Any send may name any model in the catalog** → [ADR: a chat can switch to any model](../docs/adr/2026-09-25-a-chat-can-switch-to-any-model.md).

**Writes are `src/lib/chat-outbox.tsx`**, mounted at `AppLayout` above the routes so a send settles whatever became of the composer that started it. One entry per chat, keyed by chat id or `new:<mode>`: the draft, the `pick` (model + effort), the network toggle, and one `Send` (`idle | sending | held | awaiting`). `useChatOutbox(mode, chatId, clusterId?, seed?)` is the whole API. → [ADR: the chat outbox](../docs/adr/2026-10-17-the-chat-outbox-holds-each-chats-send-above-the-routes.md).

- **Nothing moves between keys** except `moveDraft` (the deleted-chat notice's "Start a new one"). An existing chat's send goes `awaiting(seq)` until the composer sees that row and calls `settle`; a created chat's leaves the `new:` entry idle and empty.
- **A refusal is settled, a dropped response is not.** A GraphQL error returns to `idle` with the draft kept; the next submit mints a new `requestID`. A `networkError` holds the send — id, content, cluster, pick, switches, toggle, and whether it was the draft — behind Retry/Discard; Retry resends it exactly, never under the window's current cluster or pick.
- `submit`/`retry` resolve to the created chat (id + cluster) or null. The composer follows it only while mounted *and* still on that cluster — the `new:` composer outlives a cluster switch.
- **Ask again** (on the last row when it is a `Failed` answer to a question) is `askAgain(content, pick)`: a fresh send under a new `requestID` with the failed row's question and pick. It leaves the draft alone and rides the entry's one send. It is not Retry, which is the same send under the same id.
- The one refusals remembered are `KSTACK_CHAT_CONTEXT_FULL` (`{ kind: 'context-full', model }`, the model that send named), `KSTACK_CHAT_SANDBOX_CHANGED` and `KSTACK_CHAT_NETWORK_CHANGED`; the next send clears them. Send stays enabled.
- An unpicked entry takes the composer's `seed` (the last answer's model, else the catalog's first) only once both the messages `Bookmark` and the catalog have answered. **An effort belongs to its model**: falling back to another model takes that model's default.

`useModels` (`src/lib/models.tsx`) is the one reader of `models` and owns `seedPick`/`modelOf`. It separates an empty catalog (no key) from `failed` (with `retry`); a failed query is asked again **once per live watch** (`useAskAgainWhenLive`), never on every failure.

**`OpenChat` is keyed on the chat id** and owns both watches. After the list's `Bookmark`, an id the map lacks renders "This chat was deleted." A chat of another cluster renders its own notice, gated on the clusters snapshot, with `Switch to it` while that context exists. Switching cluster from the omnibox's picker clears the `chat` and `namespace` params, leaves `/chat/$chatId` for `/chat`, and clears the focused log view; `setContext` itself touches none of them.

**`ChatComposer`** (`components/widgets/chat-composer/`, exporting the composer alone; `composer.tsx`) draws the box and `ModelPicker` (`model-picker.tsx`), the model and effort selects over the whole catalog. A stored pick the catalog lacks is written back to the seed by an effect, and `canSend` reads the entry's actual pick, never a render-time fallback. Send is disabled while the watch it waits on is `connecting`, while the send is unsettled, while a new chat has no cluster, while a switch is in flight, and while the last message is `Streaming` — the last is in the guard as well as behind the button, since Enter takes the same path. Placeholders that blame the user wait for their query to answer; an empty catalog's reads *Set an API key, then restart Kstack*, since the sidecar reads keys once per launch. IME composition is respected (`nativeEvent.isComposing`). While an earlier message awaits approval, **Show** scrolls to it (`onShowWaiting`); it never approves. **A snapshot of the view rides a send** in chat mode, on a chat: the focused view while it is this chat's and the right sidebar is open, else `shownWindowOf(chatID)`'s log window. The composer reads the picked `LogViewportHandle` at the press, the sidebar's as its viewer wrote it, a window's mirror as its last push left it (`snapshotOf`, `src/lib/logs-snapshot.ts`, keeping the first 50 selected lines and sending `selectedCount`), and a chip above the box says so and names the place: *in the sidebar* or *in a window*, and *(the first K sent)* when fewer lines ride than were selected. A send never waits on a log window, so it carries that window's last push. It carries the grep the viewer runs, which the sidecar's View section puts in place of the call's. **A selection rides every send** until it changes or the user presses the chip's ×, which takes the lines out of the send and leaves them selected in the viewer: the composer holds the removed selection array and compares by identity, since the viewer writes a new array only when the selection changes. A held send keeps its snapshot; Ask again sends none.

**A send names the switches its sender saw.** `chatSend` carries the chat's `sandboxDisabled` and `networkEnabled` as the list watch has them (`false` for a new chat), and the sidecar refuses a mismatch. So Send and Ask again wait for the list to deliver the chat, and from a switch's press until the watch shows its committed value (`useChatSwitch`, `src/lib/chat-switch.tsx`, held in `ChatSwitchProvider` at `AppLayout`; wrapped by `useSandboxSwitch` and `useNetworkSwitch`). → [ADR: leaving the sandbox is the user's switch](../docs/adr/2026-09-30-leaving-the-sandbox-is-the-users-switch-for-a-chat.md).

- `useSandbox` (`src/lib/sandbox.tsx`) is the one reader of the `sandbox` query: `available`, `networkAvailable` and their reasons, `true`/`false`/undefined.
- **`SandboxPopover`** (`chat-composer/sandbox-popover.tsx`, machine with a sandbox) is the composer's *Sandbox* button: it names where the chat's commands run, off the watch (*Outside the sandbox* for an open chat that left it), and opens a popup that holds only a placeholder for now. **No control in the app leaves the sandbox**: `SandboxSwitch` (`chat-composer/sandbox-switch.tsx`; leaving confirms in a `Dialog`, returning is immediate) is mounted nowhere until the popup takes it. A chat starts sandboxed. → [outside the sandbox is the user's choice](../docs/security/2026-09-30-outside-the-sandbox-is-the-users-choice.md).
- **`NetworkSwitch`** (`chat-composer/network-switch.tsx`, open chat, in the sandbox): turning on confirms; off is immediate. The outbox entry's `networkThisTurn` is the per-message toggle: `submit` sends it, a held send keeps it, the accepted draft send clears it, Ask again ignores it. Nothing in the composer sets it yet. → [network is the user's switch](../docs/security/2026-10-04-network-is-the-users-switch.md).
- **`ChatGrants`** (`chat-composer/grants.tsx`) lists the chat's own rules. `useChatGrants` (`src/lib/chat-grants.tsx`) re-asks after a removal, on focus, and after a `Chat`/`Always` decision. **Every query or mutation that can change the rule list carries `chatGrantsContext`** (`additionalTypenames: ['PermissionRule']`) — an empty list gives urql's cache nothing to key on.

**Tool calls.** `ChatMessage.toolCalls` is every call of a turn, each with the `action` its tool in the sidecar read from its arguments (or, for `LogsView`, `LogsRead` and `LogsWatch`, what its run resolved), its `approval`, and `agentCallID` for a subagent's call. **The webview never parses a tool's arguments, a path, a URL or a host** — it draws the sidecar's fields. → [the request reads the arguments](../docs/security/2026-09-23-the-request-reads-the-arguments.md). Under an answer's text, each of the answer's own calls not awaiting approval is a closed disclosure (`ChatTranscript`, `chat-transcript.tsx`); `summaryOf` is the one reader of its summary and `toolCallTag` of its tag. Summaries go through `VisibleText` with no `title`.

- **A `Write`/`Edit` that ran unasked** (no `approval`, `Succeeded`) draws its content open under the summary, not inside the closed disclosure, since a later command may run the file.
- A memory call for every cluster carries *for every cluster* whatever its status.
- A sandboxed call's directory line says `sandboxed` (and `with network`); the request never does.
- A searching call draws under *Searched the web* alone. A `LogsView` call with an action draws as `logs-view-card.tsx`, with an eight-line window under its receipt (`logs-view-inline.tsx` over `src/lib/inline-log-lines.ts`). The chat's newest pinned `Tail` view runs live; every other card reads one page and stops. A frozen tail card ends at its *until*: the next view's `resolvedAt` when pinned, its own when not, so a reload shows the same lines. `viewEnds` (`chat-transcript.tsx`) gives each card its *until*, null for the newest. A `LogsRead` call with an action draws as `logs-read-card.tsx`: the lines the model read, from the action alone and requesting nothing, eight rows then *Show all*, with a footer saying what lay beyond them (`olderMore`, `newerMore`, then each notice). A line stamped before `since` is tagged *before*, one past the range's end *after* (`until`, else the nanosecond before `resolvedAt` when padded after), compared with `compareTimestamps`; `LineRow` mutes a tagged line. Its *View around this* sets the focused view to the read's `viewAround`, in chat mode alone. A `LogsWatch` call with an action draws as `logs-watch-card.tsx`: what it waits for, off the action, then its task's state, off `ToolCall.background` alone: *watching…* and Stop while it runs; the lines it held (eight rows then *Show all*) with why it ended; *nothing matched by* its end; a failure's reason. Why it ended can carry the cluster's words, so it is drawn through `VisibleText`. Its *View around this* sets the focused view to the task's `viewAround`, in chat mode alone. It fetches nothing.

**Approval requests** — the rules are in [Security invariants](#security-invariants); `ApprovalRequest` in `chat-transcript.tsx` is the drawing. Traps for anyone changing it:

- Requests are drawn after the answer's text and calls, in `approval.id` (UUIDv7) order, via `waitingRequestsOf` — which also returns waiting cluster writes, and which the composer's Show and the chat list's dot use. Each carries the DOM id `approvalAnchor(approval.id)`.
- **Keyed on `approval.id`**, never call or message, so pressed state never leaks to the next request.
- **Buttons are live only on a `Pending` approval while the message's `awaitingApproval` holds.** A `false` answer leaves them down; only a mutation error hands them back.
- **Approve, and every allow answer, arms only after its rect holds still for `APPROVE_ARM_MS`** (`useHeldStill`, `src/lib/held-still.ts`); Deny never waits. Tests pass `approveArmMs`; production passes nothing.
- Each request draws exactly what will run, through `VisibleText` (`src/lib/visible-text.ts`: `visibleSegments` spells invisible and reordering characters; `cutText` folds long text, and Approve waits on every fold that carries what is approved). Paths, URLs, hosts and names are never folded. Whitespace that changes meaning — `\r`, trailing spaces, a final newline, newlines at an edit's ends — is spelled or stated.
- The command heading comes from `commandHeading` off `sandboxAvailable` and the call's own `command.sandboxed`/`network` — **never from the chat's current switch**, which can flip while a request waits.
- A write's fields are read through `writeOf`: the HTML-sink lint refuses any `.write`.
- **A request with no action it can draw offers Deny alone** (*This request can't be shown.*).
- **Cluster writes and Secret reads** a sandboxed command sends are `ToolCall.clusterWrites`, drawn from the proxy's `action.summary`, the `diff` (`DiffBlock`, `diff-block.tsx`), and the raw request (method, path, media type, body). The allow answers appear only when `grantable` is set; *Always allow* refused with `KSTACK_VALIDATION_ERROR` means settings hold rules Kstack cannot read. Decided writes are tagged by `clusterWriteTag`; `approved`/`allowed` is the decision, not proof the cluster received it. → [cluster writes ask](../docs/security/2026-09-29-cluster-writes-ask.md), [the permissions engine](../docs/security/2026-10-02-the-permissions-engine.md), [the prompt names the action](../docs/security/2026-10-04-the-prompt-names-the-action.md), [Secret data is a permissioned read](../docs/security/2026-10-05-secret-data-is-a-permissioned-read.md).
- **The model's description** is drawn only by `ModelDescription` (`components/widgets/model-description.tsx`) over `descriptionLine` — one line, no `title` (a native tooltip draws it unspelled). → [the command description](../docs/security/2026-09-23-the-command-description.md).
- `WaitingApproval` is in flight like `Streaming` (`inFlight`): spinner, and the composer shows Cancel. An agent waiting does not put its message in flight.

## The log viewer's library

**`src/lib/log-viewer/` is the viewer's headless core**; its `README.md` is the whole statement. → [ADR: a log read is a window over a range](../docs/adr/2026-10-23-a-log-read-is-a-window-over-a-range.md). In brief:

- `types.ts` is the contract: a `Client` with `fetch` (a query of kind `First`, `Last`, `At`, `Continue`, `Until` or `Since`; a `Page` with `prev`/`next`/`follow` edges and `notices`) and `follow(cursor, seen)` (`Line`, `Notice`, `Ended`; a follow that cannot open throws or calls `onFailed`, and the window unpins). **Cursors are opaque**; a line whose cursor is held is a repeat, dropped. Every `Continue` from the after edge sends `seen`, the newest line held of each container; an `Until` sends the oldest.
- `LogWindow` (`window.ts`) is a React-free class holding the lines and the rules (stable keys, key 0 at the landing; only a `Tail` landing pins, then the pin is the user's; following is derived; one page per edge in flight). **It is bounded at `maxLines`** (the core's default is 5000): a page or batch past it drops lines at one edge, never on screen, and that edge reads them back from a *seam*, the farthest dropped stamp, with an `Until` or a `Since`. A dropped key comes back on another line, so the selection (`selection.ts`) prunes to `firstKey`..`firstKey + count` in a layout effect. → [ADR: a bounded log window reads its dropped lines back](../docs/adr/2026-10-24-a-bounded-log-window-reads-dropped-lines-back.md). `window.test.ts` ends in a seeded walk over `FakeClient` that checks the rules after every step.
- `LogViewerCore` (`core.tsx`) puts a fresh window, scroller and `@tanstack/react-virtual` virtualizer behind each landing. It reads intent off wheel, key, pointer and touch events, never a scroll event alone. It publishes to a `CoreStore` that readers take through `useCoreFields`, so they re-render only for the fields they draw.
- `FakeClient` (`fake-client.ts`) is the tests' client; `index.ts` does not export it, and nothing in the app imports it.
- **The directory imports `react`, `@tanstack/react-virtual` and its own files, nothing else** — no `@/`, no relative import out — and knows nothing of columns, the viewport, GraphQL or the error bus.

## Theming & window frame

**Browser-storage keys are `kstack:`-prefixed kebab-case, formed only by `storageKey`** (`src/lib/storage-key.ts`). Call sites pass the bare name. `@kubetail/ui` writes its own unprefixed `sidebar_state` cookie. Browser storage holds chrome shape (pane widths, open flags) and the history ceiling; a user *setting* goes to `host.json`.

**Every window shares one `localStorage`; each has its own `sessionStorage`.** Chrome shape (`usePersistedWidth`, `usePersistedFlag`) is an app-wide default with no live sync: the next window opens the way the last was left. The history ceiling is per-webview and lives in `sessionStorage`. → [ADR: chrome shape is an app-wide default](../docs/adr/2026-10-17-chrome-shape-is-an-app-wide-default-in-localstorage.md). Every `kstack:*` key is *disposable* in [`docs/persisted-data.md`](../docs/persisted-data.md): a bad value reads as the default, and a new or changed key updates its register row in the same commit.

`src/lib/theme.tsx` has two axes: **color scheme** (`system`/`light`/`dark` → `.dark` on `<html>`) and **skin** (reserved). The preference lives in `host.json` (`src/lib/host-file.ts` owns read/update/subscribe), never localStorage. Boot is synchronous via `window.__KSTACK_HOST__` and the inline script in `index.html`, which **hand-mirrors `resolveColorScheme`**; its boot mark shows the light or dark app icon by the `.dark` class, as `AppMark` does, pinned by the root `index.test.ts`. Keep both in sync. → [ADR: host.json settings](../docs/adr/2026-08-09-host-json-settings.md), [ADR: first-paint theming](../docs/adr/2026-08-09-first-paint-theming.md). The picker is in `settings-dialog.tsx`.

**The Settings dialog's Sandbox and Permissions sections draw only while `useSandbox` answers `available: true`.** Each has one hook that reads its queries and runs its mutations. Every path, target, context, pattern and rule line goes through `VisibleText` (`components/widgets/visible-text.tsx`). A hook re-asks its query after each mutation and on focus where the query alone carries state another window can change.

- **`PATH`** (`sandbox-settings.tsx`, `useSandboxPath` in `src/lib/sandbox-path.tsx`). Entries keep whitespace and spell trailing characters, since Include approves the folder drawn. Include sends the drawn `target`, so a refresh that moved it refuses. While the fault is set, what commands search comes from `sandboxPathResolved`, never from the list's length. → [ADR: `PATH` is the login shell's, filtered and frozen](../docs/adr/2026-10-02-path-is-the-login-shells-filtered-and-frozen.md).
- **Executables** (`SandboxExecutableList`, `useSandboxExecutables` in `src/lib/sandbox-executables.tsx`) over the `sandboxExecutablesWatch` gauge. The probe mutation answers at once and the watch carries the end. After a press, *Probe again* holds until the watch's `probes` count passes the one seen at the press — the answer and the frame race, and a gauge can fold a short probe's start into its end.
- **Folders** (`useSandboxFolders(chatID?)` in `src/lib/sandbox-folders.tsx`; `grant` runs under `chatGrantsContext`). **`FolderGrantForm`** (`folder-grant-form.tsx`) is the one form a folder is granted from, here and in the transcript; it sends the path exactly as typed. Remove is disabled while `rulesHeld`. *Never readable* is read-only. → [path grants](../docs/security/2026-10-04-path-grants.md).
- **Permissions** (`permission-settings.tsx`, `usePermissionSettings` in `src/lib/permission-settings.tsx`). It re-asks `permissionSettings` on every opening and on focus. **The hook alone spells the wire's dotted keys** (`permissions.defaultMode`, `.modes`, `.rules`); everything else uses `PermissionField`. While the file holds values Kstack cannot read, that field's edits are disabled and *Discard what Kstack cannot read* (`permissionDiscardRefused`) sits behind a confirm naming them. *Clear* acts on a context's own entry, never a pattern it matches. → [the permissions engine](../docs/security/2026-10-02-the-permissions-engine.md).

**The window frame is per-platform** (macOS native / Windows frameless-opaque / Linux frameless-transparent). `WindowFrame` (`window-frame.tsx`, at `__root.tsx`) paints Linux's border and shadow. `WindowResizeHandles` is its **sibling**, never a child — the frame's `contain: paint` would clip it. `main.tsx` adds `<html class="frameless">` on Linux only. **Full-height screens use `min-h-(--app-min-h)`, never `min-h-svh`.** Maximized Linux goes full-bleed (`useWindowMaximized`). → [ADR: per-platform window chrome](../docs/adr/2026-08-09-per-platform-window-chrome.md).

Off macOS there is no native menu bar: `AppMenu` (`app-menu.tsx`) owns `Ctrl/Cmd+N`/`Ctrl/Cmd+Q` and invokes `new_window`/`quit`; `WindowControls` (`window-controls.tsx`) draws the caption buttons.

## Text boxes

**Every text box turns off the webview's autocomplete, autocorrect, autocapitalize and inline predictions** (`writingsuggestions`, WebKit's). ## Cursors

**Controls and in-app links use the default arrow cursor, as native desktop apps do.** `index.css`'s base layer sets it on `button`, `[role="button"]` and `a[href]`, overriding `@kubetail/ui`'s `cursor: pointer` and the browser's hand on links. Every link today is in-app navigation (the sidebar, the mode switch, the chat list). ## GraphQL — never talks HTTP directly

The webview has **no network access**. urql routes everything through Tauri IPC (`src/lib/graphql/`): queries and mutations via `invoke('graphql_query')` (`invoke-fetch.ts`), subscriptions via `graphql_subscribe`/`graphql_unsubscribe` over a Tauri `Channel` (`subscribe-exchange.ts`, with its own capped-backoff reconnect). Read `src/lib/graphql/client.ts` and its tests before touching transport or retry logic. → [ADR: GraphQL over Tauri IPC](../docs/adr/2026-08-09-graphql-over-tauri-ipc.md).

**A `next` frame marked `extensions.watchFailed`** is the sidecar naming why a watch died. `subscribe-exchange` sends it down the drop path (report, hold last-known data, reconnect), never to the urql sink, which would re-deliver the last frame's data. **Key on the marker, never on shape**: a live frame with a field error looks the same. A reconnect dials with the operation's variables, or with what its context's **`reconnectVariables`** answers — `logsFollow` hands one in to resume past the newest line it handed on of each container. → [ADR: watch-failure reporting](../docs/adr/2026-08-14-watch-failure-reporting.md).

**Connection lifecycle is the transport-status registry** (`transport-status.ts`): `connected` and a process-wide monotonic `generation`, bumped on the host's **`open` frame**, never on the `graphql_subscribe` ack. Consumers use **`useWatchSubscription`** (`use-watch-subscription.ts`), never raw `useSubscription`; it generation-gates its accumulator. urql shares one connection per query + variables, so a consumer mounting into a running stream never sees its snapshot. Where a watch has several consumers and one can mount late, either hold the one watch in a provider above them all (`ClusterCachedDataKindsProvider`) or set **`unshared: true`**, which costs a connection and a cold list per instance, so it is not the default. `watchPhase(synced, connected)` gives `connecting` (no snapshot yet), `live`, `reconnecting`. → [ADR: transport-status generation](../docs/adr/2026-08-09-transport-status-generation.md).

**Frames are reduced as a batch**, once per `requestAnimationFrame` or after 250ms, whichever is first. The reducer gets `frames: Data[]` (never empty). A map reducer copies once per batch and applies frames in place (`applyChange` mutates); a simple per-frame fold is lifted with `perFrame(step)`. A series (root `CLAUDE.md`) folds through `seriesReducer(frameOf)`: append, keep the last window ÷ interval points, an empty first frame folds to an empty series. → [ADR: a series is a third kind of stream](../docs/adr/2026-11-02-a-series-is-a-third-kind-of-stream-and-the-pool-owns-its-clock.md). A frame from a newer connection drops the pending batch. A test that pushes a frame and asserts on the next line calls `flushWatchesSynchronously()` from `@/test-utils` at module scope. → [ADR: batch per animation frame](../docs/adr/2026-08-30-batch-watch-frames-per-animation-frame.md).

## Lint / build

- `pnpm lint` (oxlint, then `oxfmt --check`) → `make lint-ts`. Run before committing. `pnpm format`
  writes, sorting imports too. → [ADR: lint the webview with oxlint's categories](../docs/adr/2026-11-05-lint-the-webview-with-oxlints-categories-and-a-chosen-rule-list.md),
  [ADR: oxlint's native React compiler rules](../docs/adr/2026-11-05-lint-the-react-compilers-rules-with-oxlints-native-ports.md)
- **Linting is oxlint** (`.oxlintrc.json`): the `correctness`, `suspicious` and `perf` categories,
  rules from the other categories named one by one, and type-aware rules through `oxlint-tsgolint`.
  A rule an enabled category already turns on is listed only to give it options or turn it off,
  with the reason beside it. **Every rule is an error and a warning fails the run.** Kstack's own
  rules are `lint/oxlint-plugin.js`, tested in `lint/oxlint-plugin.test.ts`.
- **Tailwind classes are `pnpm lint:tailwind`** (`.oxlintrc.tailwind.json`, `make lint-tailwind`),
  a run apart from `pnpm lint` because loading Tailwind takes most of its ~6s. It checks `className`
  and `cn(...)` against `src/index.css`'s design system: the canonical spelling (`wrap-break-word`,
  not `break-words`; `size-4`, not `h-4 w-4`), no class Tailwind does not know, and no two classes
  setting the same property. `pnpm lint:tailwind --fix` rewrites a spelling. A class string built
  anywhere else is not checked. Order and wrapping are `oxfmt`'s. **Run it after changing classes.**
  CI's `TypeScript · Lint` runs it.
  → [ADR: lint Tailwind classes in a run of their own](../docs/adr/2026-11-05-lint-tailwind-classes-in-a-run-of-their-own.md)
- **What the rules ask for**: no `any` and no value typed `any` outside tests; `toSorted` and
  `toReversed`, never a `sort` or `reverse` in place on an array others hold; `??` for a nullish
  default, `||` where an empty string or `false` should fall through; a default prop that is an
  object, array or function is a module constant. `for…of` is allowed, `for…in` is not.
- **A switch over a union lists every member** and needs no `default`; a `default` does not stand in
  for a missing one. Any other switch has a `default`.
- **`tsc` checks fallthrough, implicit returns and `import type`** (`noFallthroughCasesInSwitch`,
  `noImplicitReturns`, `verbatimModuleSyntax`); the lint has no rule for them.
- **A disable comment is `oxlint-disable…` and gives its reason**:
  `// oxlint-disable-next-line <rule> -- <why the rule is wrong here>`. `kstack/disable-needs-reason`
  fails one without, an unused one fails, and `eslint-disable` comments are not read.
- **A promise nothing awaits is marked `void`** (`typescript/no-floating-promises`): an urql
  mutation or a `navigate` fired from a handler, for example. A JSX handler may return one.
- **Formatting is oxfmt** (`.oxfmtrc.json`), which also sorts imports: packages, `@/`, then relative
  paths, a blank line between. The `lint`/`format` scripts pass **globs only**: a directory
  argument mixed with a glob silently narrows to the glob's extensions. `.vscode/settings.json` runs
  the same binaries in the editor (`oxc.oxc-vscode`, resolved from `node_modules`).
- The **React compiler** is on in two places that must stay in step: the babel transform
  (`vite.config.ts`, off in `--mode coverage`) and oxlint's native ports of the compiler's rules
  (`react/purity`, `react/refs`, `react/exhaustive-deps`, …: `recommended-latest`'s set, in
  `.oxlintrc.json`). A disable comment names them `react/…`. A bail-out on a broken rule is a lint
  error; one on syntax the compiler does not support yet (`react/todo`, such as `??=`) is silent.
- **Write as though the compiler weren't there** — it bails per-function, silently. So
  `react/exhaustive-deps` is an **error**, and manual `useMemo`/`useCallback` are ordinary
  tools.
- In the Linux sandbox, `node_modules` is symlinks into a store every worktree shares, and a package resolves only the dependencies it declares. Never edit a file under it. An error seen only there is most likely an undeclared dependency → [ADR: share one pnpm store across sandbox worktrees](../docs/adr/2026-10-28-share-one-pnpm-store-across-sandbox-worktrees.md).
- **An `*.svg?react` import is a React component** drawing the SVG inline (`vite-plugin-svgr`, in `vite.config.ts`); a plain `*.svg` import is a URL.
- `pnpm build` = `tsc -b && vite build`. Dev: `pnpm dev` (webview) or `pnpm tauri dev` (full app).
