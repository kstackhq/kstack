# Security record — the bash tool, 18 September 2026

**Subject:** the model can run a command on the user's machine, once the user approves that
exact command. Chat offers the Messages API's `bash_20250124` client tool on every Anthropic
model (`sidecar/internal/services/chat/command.go` and `bash.go`, `sidecar/internal/shelltool`); the model asks, the
card shows the command, and the sidecar runs `bash -c` after the user presses Approve. The
living model is [security-model.md](../security-model.md); the ADR the loop rests on is
[a tool call is a committed row before it runs](../adr/2026-09-17-a-tool-call-is-a-committed-row-before-it-runs.md).

## What now runs

**The model's text, as a process on the user's machine, as the user**, with the environment
Kstack runs with — on macOS the allowlist the shell import took (`PATH`, `KUBECONFIG`, the cloud
credential variables), on Linux the launcher's; never a provider key, which `takeProviderKeys`
(`sidecar/config.go`) strips from the process before either. Never before this change did
anything the model wrote execute anywhere but in the model. The bound is not the prompt and not
a parser: **it is the user reading the command and pressing Approve**, every time
(`TestACommandWaitsOnTheUser`, `TestADeniedCommandDoesNotRun`, `TestACancelledWaitRunsNothing`).
There is no allowlist of commands, because one that lets a tool through lets that tool's every
subcommand through, and a command the user did not read is a command the model ran.

The cluster is not this tool's job. The prompt (`prompts/command.md`) says so — what the cluster
tools answer, ask them; do not reach for `kubectl` in a shell — and what the model needs from a
cluster will come as tools of the sidecar's own, each bounded and recorded on its own terms.

## Prompt injection

An injected instruction can make the model *ask* for any command. It cannot make one run. The
card shows the command verbatim, as the string bash receives, so an instruction hidden in a
label reaches the user's eye as the command it produced. The scratch directory sets where an
approved command starts, not what it can reach: an approved `rm -rf ~` runs, and an approved
command reaches every cluster and account the user's shell can. The user's eye is the bound.

## Input handling

`command` is a string handed to `bash -c` unexamined; that is the tool's contract and the reason
for the gate. `restart` runs nothing and empties the scratch — by removing the entry and making
it again, never by walking into it, since an approved command can have replaced the scratch with
a symlink and a walk would delete what it points at (`TestRestartDoesNotFollowAReplacedScratch`);
a restart queued behind a command is refused once the turn is cancelled
(`TestACancelledQueuedRestartRunsNothing`). Anything else — both, neither, an
unknown key — is refused `bad-input` with no card (`TestABadBashInputIsRefused`).

## What comes back

The output, redacted with the stored error path's patterns (`safe.Redact`) and then cut at
16 KiB (`commandResultBudget`) — in that order, so a token across the cut is whole when the pattern
sees it — into the record and the transcript (`TestACommandResultIsRedactedThenCut`). The user
approved the command that produced it, so a secret it prints is one they asked to see; the
redaction is for the token a verbose command prints in passing. The patterns are `safe`'s as they
are, URLs included: every URL in the output loses its query string and its userinfo, so an
approved `curl -v` comes back with its URLs cut. Accepted, and stated here so it is not read as
token-only. The residual is a token across the 64 KiB capture limit (`commandCaptureLimit`).

## The record

Every command is a `tool_calls` row committed before the wait (`pending`, then
`awaiting_approval` with `is_mutating` and the `tool_use_id` that joins it to its block), with an
`approvals` row that says what was asked, when, and what the user decided; the output is the
row's `result` or `error`, and `started_at` says whether bash ever ran — set by one write, the
committed `running` row the moment before it starts — which is what the transcript's *not run*
and *may have run* rest on (`TestACommandRowStartsPending`, `TestACancelledRunIsInterrupted`,
`TestStartupFailsAStrandedWait`). A cancelled or stranded wait leaves `pending` on the approval
row, which is the truth. A write that fails between the decision and the start refuses the
command rather than running it unrecorded (`TestAFailedApprovalWriteRefusesTheCommand`). The
transcript reads every command off the row, never off the message's content, so a command whose
block never reached the stored content is still shown (`TestACommandSurvivesACrashBeforeItsCheckpoint`).

## What cleanup does not reach

The process group is killed after every run — when the context ends and again after bash exits
(`TestRunKillsTheGroupOnTimeout`, `TestRunKillsWhatACommandLeftBehind`). A descendant that left
the group (`setsid`, a daemon that calls `setpgid`), or anything running when the sidecar itself
is killed, is the user's to find. An approved command is the user's process in every sense.

## Consent

Per command, in the transcript. No setting turns the gate off, and a spec that adds one — an
allowlist, "always allow reads", "trust this chat" — is a new record. A child agent is never
offered the tool (`TestTheChildIsOfferedItsAllowlistAlone`); a Windows chat is offered it only
where Git for Windows is installed (the addendum below).

## Audit, the same day

A pass over the landed commit against this record, tracing the command from the model's
`tool_use` to bash and its output back to the provider. What holds, what is sharpened, and the
one gap it opened, each with where it is now written.

**The card is the command.** The string the card shows and the string bash receives are one
decode of the same `tool_use` input (`parseBashInput` for the run, `commandLine` for the
record), so what the user reads is what runs, byte for byte; `TestACommandWaitsOnTheUser` pins
the two against each other. The approval id is minted in the sidecar and shown only after the
row and its approval are committed, and a decision is delivered to a waiter registered before
either, so no id is ever guessable or decidable ahead of its card. A second decision, a decision
after a cancel, and a decision after a restart of the sidecar each find no waiter and change
nothing (`TestACancelledWaitRunsNothing`, `TestStartupFailsAStrandedWait`). A cancel that
lands beside a decision wins, and the approval row keeps `pending`.

**The gate is the page, not the page's code.** `chatApprove` takes the approval id and nothing
else, and the id rides the messages watch every window reads. So a script running in the
webview — a dependency that executes — can approve every command the model asks for, and a
prompt injection that makes the model ask reaches the user's shell through it. This is the
webview's standing authority, widened: before this change it read the mirror and wrote app
state; now it holds a shell behind a card it can click itself. Written into the *Webview →
host* boundary and *Two facts* in [security-model.md](../security-model.md), and the root
`CLAUDE.md`'s invariants, so the CSP and the no-remote-script rule are understood as what keeps
the eye the user's.

**The eye must be able to read.** The card draws the command as text, exactly — which is the
right rule and also the gap: a bidirectional override, a zero-width character, a control
character, or a wall of newlines ahead of the real command is drawn as it is, so a command
composed to read as one thing and run as another (the Trojan Source shape) passes the eye that
is the bound. Nothing in the webview makes such characters visible today, and nothing bounds a
command's length on the card. Recorded as **Not built** in the model and as a gap in
[`TODO.md`](../TODO.md#security) with its shape.
*Closed the same day:* `src/lib/visible-text.ts` spells the characters out and folds the length, Approve waits on the fold, and the row in the model is **Enforced**.

**The environment, sharpened.** On macOS the allowlist the shell import takes holds paths and
identities — `PATH`, `KUBECONFIG`, `AWS_PROFILE`, the config-file and credential-file *paths*,
`GOOGLE_APPLICATION_CREDENTIALS` as a path — and no credential value, so an approved `env`
prints where the credentials are and not what they are. On Linux the environment is whatever
the launcher gave the sidecar, which is the user's session's, values included; the environment
is trusted, and this record does not make it a bound. `BASH_ENV` in that environment would have
bash source a file before the command; that file is the user's own. No provider key is in either
(`takeProviderKeys`).

**What redaction covers, stated.** `safe.Redact` blanks the provider keys the config read, an
`authorization`/`cookie`/`api-key` header line, a URL's userinfo and query, a bearer token, a
JWT and an `sk-` key. A kubeconfig's `client-key-data`, an AWS access key pair, a PEM block or an
`.aws/credentials` line has no rule and goes to the provider as printed, after the user approved
the command that printed it. The model's redaction row now names the shapes and the residual, so
"redacted" is not read as "no secret leaves".
*Closed:* `safe.Redact` now knows what a cluster command prints — a PEM private key, a credential
field of a kubeconfig, a cloud credentials file, a service-account JSON, a token response or an
environment dump, a long flag's value, a `.netrc` password, an AWS access key id and the tokens
with an issuer prefix. The residual is stated in the model's row.
*Clarified:* redaction is hygiene against accidental spillage, never a boundary. The model chooses
the command, and a command can re-encode its output past any rule (`… | base64`), so the card
stays the bound and the rules cover the shapes real tools print. A printed form interrupted
before its closing delimiter — by the capture limit, a kill, or a value's own blanks or newlines
— can leak past its first token; that class is the model row's stated residual, and a new
instance of it is the residual restated, not a defect to fix per input.

**The stored read can name a different command than ran.** `parseBashInput` and `commandLine`
are `encoding/json`, which matches a key case-insensitively and lets the last duplicate win, so
`{"command":"ls","Command":"rm -rf ~"}` runs `rm -rf ~` and the live card says so; the stored
read's `json_extract(t.arguments, '$.command')` matches the key exactly and, once the turn
settles, draws `ls`. Nothing runs unshown — the card is the live message — and
`approvals.summary` keeps the string that ran; what breaks is the transcript's history, which
this record promises reads off the row. Recorded as a gap in [`TODO.md`](../TODO.md#security):
one strict decode that refuses any key but the two, so the two readers agree by construction.
*Closed the same day:* `readBashInput` is that decode, `messageCommands` refuses the same keys, and the row in the model is **Enforced**.

**Nothing new is logged.** The command and its output are written to `tool_calls` and
`approvals` and to no log line; the three `slog.Warn`s on the path carry a store error alone.

**The scratch is the working directory and nothing more.** It is under the data directory —
owner-only by mode on Unix, the profile ACL on Windows (the addendum below); a restart or a
close removes the entry without following a link a command may have put in its place
(`TestRestartDoesNotFollowAReplacedScratch`). An approved command is not confined to it.

## Addendum, the same day — Windows

Windows chats are offered the tool where Git for Windows is installed. Its bash is found
through Git's own install record — `SOFTWARE\GitForWindows` under `HKLM` in both registry
views, then `HKCU` — and never off `PATH`, where `System32\bash.exe` is the WSL launcher: a
WSL shell sees a Linux filesystem and a kubeconfig of its own, the opposite of the machine the
user's terminal shows (`TestNewDeclinesWithoutGitBash`). The process tree is a job object with
kill-on-close, terminated when the context ends and again after bash exits; nothing under its
flags can spawn outside it, and a sidecar crash closes the handle and kills the descendants
with it — a guarantee the Unix group does not make. A process a command started through an
out-of-job broker (a scheduled task, WMI, ShellExecute) is outside the guarantee, as a
descendant that left the Unix group is.

**The command travels as a file, never on a Windows command line.** The kernel takes one
command-line string and the MSYS runtime parses it back, so bytes on that line are bytes
something else interprets. The approved bytes are instead written to a file beside the scratch
and bash runs the file; `TestRunDeliversTheCommandByteForByte` pins the round-trip. That file
is a third place the command is written, beside `tool_calls` and `approvals` (*Nothing new is
logged*, above): under the data directory for the run's duration, removed after it, and one a
crash or a failed remove leaves until the next start sweeps the root. It is written read-only,
so an ordinary append fails — but bash reads a script incrementally, and a command that clears
the attribute and appends to `$0` executes what it appended. That grants nothing, since the
command was approved and could run the appended text directly; what it bounds is the promise:
**what the card showed is what bash was handed**, not a bound on what ran. The same is true of
`bash -c` on Unix; it is only worth stating where the script is a file the command can reach.

**The scratch's protection differs by platform.** The 0700 is real on Unix
(`TestOpenMakesAnOwnerOnlyScratch`); on Windows a mode is advisory and the scratch inherits
the profile ACL under the data directory, the decision every cache file already rests on
([ADR](../adr/2026-09-02-windows-cache-files-rely-on-the-profile-acl.md)). And the environment
paragraph's claim holds through a translation: Git Bash rewrites `PATH` into POSIX form and
`HOME` falls back to `%USERPROFILE%`, so a command sees the Git Bash terminal's view of the
same process environment, not a copy of it.

## Note, 19 September 2026

The contract's shape — the input's decode and the result — is `AnthropicBash` in

## Note, 22 September 2026

The tool is rebuilt (spec 22) as one custom function, `bash`, on every dialect: the definition
the request carries and the sidecar runs, in `sidecar/internal/tools/bash`, with the gate in the
loop (`agent`'s `Approver`) and the rows in `services/chat/approval.go`. One command and one card per
call, and a reply's cards are put to the user one at a time
([ADR](../adr/2026-09-22-the-gate-is-the-tools-card.md)). The input is `{command}` alone, and an
empty command is refused (`TestAnEmptyCommandIsBadInput`), since it would still start bash,
which sources `BASH_ENV` first.

**No scratch, no restart.** A command starts in the user's home directory, as a new terminal
does, so it means what the user reading it expects. What this record tied to the scratch retires
with it: the owner-only mode (`TestOpenMakesAnOwnerOnlyScratch`), the restart that must not
follow a replaced scratch (`TestRestartDoesNotFollowAReplacedScratch`, on both platforms), and
the restart queued behind a cancelled command, which is now any call queued there
(`TestACallQueuedBehindACancelledWaitRunsNothing`). A file a command writes by a relative path
lands among the user's own; the prompt steers throwaway files to `mktemp`, and the user reads
the command before it runs. On Windows the command's script lives under the data directory
(`<dataDir>/shell`), swept at start, never in the home directory. A working directory of each
chat's own, under the data directory, is the follow-up.

The protections above otherwise hold, with these names moved: `TestACommandRowStartsPending` is
`TestACommandRowStartsAwaiting`, since a gated call's first write is now `awaiting_approval`
with its approval; `TestABadBashInputIsRefused` is `TestBashReadsOneCommand`, the token walk
`ApprovalText` and `Run` share; `TestTheSessionEnvironmentIsTheProcessOwn` is
`TestACommandsEnvironmentIsTheProcessOwn`. The mutation this record calls `chatApprove` is
`approvalDecide`, named for the approval it decides; it takes the approval id and nothing else,
as before.

**Built and not offered.** `app.go` leaves bash out of the box every turn is offered until the
webview draws the approval card, so no turn is offered it yet. Wiring it widens who can ask for
a command: every Chat Completions vendor and every local model whose catalog entry takes tools,
where this record covers the Anthropic row alone. The change that wires it carries a new
security record for that widening.

## Note, 22 September 2026 — the version

`bash.New` now runs the bash it found once at startup, as `bash --version`, bounded at two
seconds and with no console on Windows, so the prompt can name the version. `--version` exits
before bash reads any startup file, so nothing of the user's runs; `-c` would source `BASH_ENV`.
The output is parsed to a major.minor or dropped, and a failed read still offers the tool
(`TestNewReadsTheBashVersion`).

## Note, 24 September 2026 — the cluster

*The cluster is not this tool's job*, above, no longer describes the prompt. No cluster tool is
offered, and bash's prompt now lets the model reach the cluster with `kubectl`, `helm` or `flux`
as the last resort, each command naming the chat's context: [the cluster through the
shell](2026-09-24-the-cluster-through-the-shell.md). The gate is unchanged.
