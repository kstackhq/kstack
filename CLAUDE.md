# Kstack

A Kubernetes desktop app. Three parts that talk to each other:

- **`src/`** — React webview (this file's focus).
- **`src-tauri/`** — Tauri/Rust native host (windows, tray, sidecar lifecycle). See `src-tauri/CLAUDE.md`.
- **`sidecar/`** — Go sidecar (GraphQL API, Kubernetes + cloud logic). See `sidecar/CLAUDE.md`.
- **`proto/`** — shared gRPC contract (host↔sidecar). Single source of truth, compiled to Go (committed, via `protoc`) and Rust (via `src-tauri/build.rs`). Run `make proto` after editing.

The **`Makefile` is the polyglot entry point** — Go/Rust/JS commands meet there (`make test`, `make lint`, `make vet`, `make proto`, `make cover-go`, `make cover-js`). The Go sidecar deliberately lives outside `package.json`. Its build is `scripts/build-sidecar.go` (`make sidecar` runs it), and `tauri dev`/`tauri build` call it with `go run` rather than `make`: on Windows Tauri runs them through `cmd.exe`, where there is no POSIX shell and `bash` is WSL's. Recipes may be `sh`; those two commands may not.

**Building inside a Linux sandbox (macOS host).** `scripts/sandbox-dev-setup.sh` **must run before any build, test, or install command** — a `SessionStart` hook in `.claude/settings.json` runs it automatically, and it's idempotent, so just run it yourself if you're unsure. It isolates the Linux build outputs under `.sandbox-linux/` so the host's macOS `node_modules` etc. are untouched; without it, a `pnpm install` here overwrites the host's native binaries and vice versa. Cargo is the exception — its `target/` goes on the sandbox overlay, because the host mount's directory metadata is not coherent enough for it and a build there never converges. It no-ops outside the sandbox. Details: → [ADR: sandbox build-output locations](docs/adr/2026-09-03-sandbox-build-output-locations.md). See README for the one-time toolchain install.

## Host↔sidecar transport

The host and sidecar share a single Unix socket / named pipe. **GraphQL** (webview↔sidecar) rides HTTP/1.1 (POST + SSE); **gRPC** (host↔sidecar control: tray auth watch, login/logout, resync poke) rides HTTP/2. Both are multiplexed by **h2c** in the sidecar's `internal/app`; no TLS (the socket is user-restricted). The cluster surface is **GraphQL-only** — no gRPC kube channel. → [ADR: single-socket h2c](docs/adr/2026-08-09-single-socket-h2c.md).

**The caches fill.** Every `Cluster`, `ClusterCache`, `ClusterCachedKind` and `clusterCachedData*`
field answers: a reachable cluster whose credentials can read `kube-system` gets a cache, the cache
controller arms `kubesync` and mirrors what the cluster serves into one `ClusterCachedKind` record
per kind, and each record arms that kind's sync — a cold list, then a watch applying deltas. Every
record's `events(...)` field serves the control-plane timeline behind it, and so does a
subscription: `clusterEventsWatch(id: ClusterID!)` for a cluster, `eventsWatch(id: ObjectID!)`
for a cache or a kind. → `sidecar/CLAUDE.md`.

Cluster data streams as **Kubernetes-style delta watches** (an `Added` snapshot, one `Bookmark` closing it, then per-object `Added`/`Modified`/`Deleted`): `clustersWatch` and `clusterCachesWatch` (both unscoped), and the cache-scoped `clusterCachedKindsWatch` (opened only by whoever is looking at a cache). The sync verdict rides `clusterCacheHealthWatch`, which is **a gauge, not a delta watch** — current-on-subscribe, so no `Bookmark` closes it and none of the Bookmark discipline below applies. Each kind is its own stream; the webview keys each into a map and **joins client-side**: a cache carries `clusterID`, so caches join onto clusters by it, and a per-kind record carries an `owner { id kind }` ref, so kinds join onto caches by `owner.id`; the verdict gauge keys on its own `cacheID` (a gauge is not an owned record). **A cluster's id is the `ClusterID` scalar** — opaque text, its clusters row in the sidecar's `app.db` — and every other record's is `ObjectID`; neither is ever built or parsed by the webview. The `Bookmark` carries no entity (every change wrapper's entity field is nullable for it alone) and marks the snapshot complete — **never render an empty state before it lands**, or a populated table reads as empty for as long as the server takes to list it. **Detect it as `type === 'Bookmark'`, never as a missing entity**: a nested non-null field erroring nulls its parent, so a null entity also arrives on ordinary changes, and reading one as the snapshot boundary declares a still-loading collection complete. A change with no entity is dropped, not folded. → [ADR: delta-watch protocol](docs/adr/2026-08-09-delta-watch-protocol.md). The kube-context picker derives its list from `clustersWatch` (`src/lib/kube-config.tsx`).

**The sidecar never filters what it streams**, so a record awaiting deletion arrives like any other, carrying `deletionRequestedAt`; `Deleted` means its row is gone, and the mark that starts a teardown is an ordinary `Modified`. A cluster's delete is that mark: `clusterDelete` returns as soon as the row is marked, and the sidecar tears the runtime and the cluster's chats down behind it before the row goes, so the `Deleted` can take a moment. **Only the `Deleted` is promised**: a teardown fast enough folds the mark into it, so a row can go without `deletionRequestedAt` ever being seen — never gate a removal on having seen the mark. Deciding what to do with a dying record is the client's, and `ClustersProvider`'s fold makes it once — a tombstoned row folds as a removal, so no view has to remember. Render "Deleting…" there instead if that becomes the better answer; don't scatter the check into views.

>
> **Rationale lives in ADRs, not here.** These files state *what is true now* — invariants, conventions, commands, traps. *Why* a design was chosen, and what we rejected, goes in `docs/adr/` (see [`docs/adr/README.md`](docs/adr/README.md)) and is linked from here. When a decision changes, write a new ADR, flip the old one's status, and repoint every link in the same commit — a `CLAUDE.md` must never link to a superseded ADR.
>
> **Security is recorded in two files.** [`docs/security-model.md`](docs/security-model.md) states what is protected now and which protections a test actually pins; [`docs/security/`](docs/security/) holds dated review records, append-only like ADRs. Gaps live in [`docs/TODO.md`](docs/TODO.md#security), and a risk we decide to accept becomes an ADR plus a **By decision** row in the model — so an accepted risk never reads as an unnoticed one. When you change a boundary or land a protection, move its row in the same change.
>
> **Keep comments current — describe the present, not the past.** Code comments (and these docs) must describe only the *current* state of the code. **`docs/adr/` is the sole exemption** — ADRs are an append-only historical record and are meant to say what we rejected, replaced, and believed at the time. When you change something, update the comments around it instead of layering on history: don't leave notes about how the code *used to* work, what a field was *renamed from*, what machinery was *removed*, or which past refactor got you here. A reader should never have to reason about a prior version. State current design and rationale directly; drop "used to", "no longer", "formerly", "superseded", and similar backward-looking framing. (Contrasts with *external* systems — e.g. "unlike apimachinery's default" — are fine; they describe present behavior.)

## Writing standards

Applies to every hand-written file in the repo — Go, Rust, TypeScript, Markdown. Not to generated output (`src/gql/`, `sidecar/graph/generated*`, lockfiles), which is nobody's to hand-tune.

1. **Code — simple, idiomatic, easy for a human to follow.** Prefer the boring construction. Match the idiom of the file you are in over the one you would pick on a blank page. Cleverness that needs a comment to survive review is usually the wrong trade.
2. **Comments — terse, necessary, easy for a human to read.** Say what the code cannot: the *why*, the invariant, the trap that made this shape necessary. Never restate what the line already says. A comment justifying a choice the code no longer contains is dead weight — state the current design, don't argue against the alternatives you rejected (that is what `docs/adr/` is for).
3. **Documentation — simple, concise, easy for a human to read.** Lead with what is true now. One idea per sentence.

The failure mode to watch for is a comment addressed to a *reviewer* — someone who just watched the reasoning — rather than to a reader opening the file cold. The tell is a comment that spends its length on the option **not** taken.

A `UserPromptSubmit` hook (`scripts/writing-standards-hook.sh`, wired in `.claude/settings.json`) restates this at the start of every turn, since the rule has to be in mind *before* anything is composed. Keep the script's short form in sync with this section.

## Testing conventions (all three languages)

These apply to `src/`, `sidecar/`, and `src-tauri/` alike; each area's `CLAUDE.md` adds its own tooling on top.

**While working, run `make test-changed`** — the tests your changes touch, in each language (`scripts/test-changed.sh`). Don't run `make test`, `make cover-js` or `make cover-go` locally unless asked: CI runs every suite and both coverage gates on every PR. Raise a coverage threshold when CI reports the number rose.

**Every test file sits beside the file it covers.** `foo_test.go` / `foo.test.ts` tests `foo.go` / `foo.ts`. A test file with no counterpart means the unit under test is buried in a larger file — split the *implementation* out to match the test's name rather than renaming the test to match the monolith. The one exception is a file that exists solely to hold shared fixtures (`testutil_test.go`), which tests nothing.

**In Go, a platform-specific test goes in a platform-named file, never behind a `runtime.GOOS` check.** `foo_unix_test.go` (`//go:build !windows`) beside `foo_test.go`, matching how `internal/ipc` splits its implementation. The build constraint is the mechanism the language already has: a `GOOS` skip compiles the test everywhere and then declines to run it, so the file's name no longer says who it is for and the assertion silently disappears on the platform it was written for. **Split rather than skip** — a test that is *partly* platform-specific keeps its cross-platform half in the plain file, so neither half is a subset of the other (`atomicjson`'s `TestSaveCreatesMissingDirs` and `TestSaveIsOwnerOnly`). A Unix path (`/tmp`, `/srv/app`) is not absolute on Windows, and a reader holding a file open keeps a rename from replacing it there, so both belong to the Unix half.

**A test closes what it opens before it ends.** Windows removes no open file or directory, so a handle a test leaves behind — a fake's output file, a service built and never closed, a goroutine a cancelled call left running — fails `t.TempDir`'s cleanup there alone. Close it in a `t.Cleanup` registered after the `TempDir`, and wait out such a goroutine through the unit's test seam (`write`'s `TestWriteSetsTheStamp`).

**No magic sleeps — never block on the wall clock to let something happen.** A real delay is flaky under load and slow in aggregate, and it fails at the *end* of the wait rather than the moment the invariant breaks. Per language:

- **TypeScript** — `vi.useFakeTimers()` + `advanceTimersByTimeAsync`, `await waitFor(...)`, or a `flush()`/`act` helper. Never a bare `setTimeout` wait.
- **Go** — wait on a channel, not a duration: `testutil.Probe`/`Signal`, `testutil.Recv`/`Wait`, or `require.Eventually`. Never `time.Sleep`.
- **Rust** — `#[tokio::test(start_paused = true)]`, which auto-advances virtual time between parked timers. `src-tauri/src/services/sidecar/ipc.rs` (`connect_retries_until_endpoint_appears`) is the reference.

**Pace a timing-dependent unit by parameter, not by constant.** A production constant a test must outwait (a retry cadence, a poll interval) becomes an argument, and production passes the constant — see `prefsync`'s `withBackoff`. Shrinking it in a test is then free, and the test never encodes the production number.

Two shapes are *not* magic sleeps, and both must say so in a comment:

- **A negative assertion** ("must NOT happen") has no event to wait for, so it needs a bounded window. Write it as a `select` on the tripwire channel versus `time.After` — it fails the instant the thing happens rather than at the end — and size the window as a multiple of the (shrunk) cadence, never a bare guess. Sample the baseline off the same channel, not by polling a counter, or the baseline read races the bug and swallows it.
- **Latency injected into the code under test** — a fake that takes a moment on purpose so a join-vs-no-join race has a determinate answer. The test's own assertion path stays immediate.

## Commits, pull requests and issues

How a change is proposed and landed, whatever it touched. Applies to every commit,
pull request and issue in this repo, all three languages.

- **Commits are terse conventional commits, written for a human reader.**
  `type(scope): subject` —
  `feat`/`fix`/`perf`/`refactor`/`test`/`docs`/`chore`, scope only when it adds
  information (`sqlite`, `edges`, `watch`), `!` for a breaking change. Subject
  is imperative, lower-case, no period, ≤72 chars, and says what the change
  does, not how (`feat(edges): enqueue an edge's source when the declaration
  commits`). No body unless the why isn't obvious from the diff — then 1–3
  plain sentences, no bullet lists; rationale longer than that is an ADR the
  body links. Optimise for someone reading `git log`: the subject is the whole
  message for most commits, so spend its budget on what changed, never on
  restating the diff or padding the format.
- **Pull requests follow
  [`.github/pull_request_template.md`](.github/pull_request_template.md)**: keep
  its sections (`Summary` for the why, `Key Changes` for the what, `Checklist`),
  and lead the title with the template's emoji for the change type — 🎣 bug fix,
  🐋 new feature, 📜 documentation, ✨ general improvement. Titles must be natural
  titles with first letter capitalized, not conventional commit headings.
- **A spec never reaches `main`.** It is proposed as a
  draft PR labelled `spec` and titled `📜 Spec: …`; once accepted it merges
  into a `wip/<topic>` branch, implementation PRs target that branch, and a PR
  from it lands the work on `main` and deletes the spec. → [`docs/specs/README.md`](docs/specs/README.md),
  [ADR: a spec never reaches main](docs/adr/2026-10-03-a-spec-never-reaches-main.md).
- **An issue that describes work to be done follows
  [`.github/ISSUE_TEMPLATE/task.md`](.github/ISSUE_TEMPLATE/task.md)** — a bug,
  an improvement or a feature someone can pick up. Keep `Summary` and
  `Done when`; the sections between them fit the work. The title is imperative
  with the first letter capitalized, no emoji. A bug not yet understood uses
  `bug_report.md`, and a request with no plan yet uses `feature_request.md`.

## Security invariants

The whole picture is [`docs/security-model.md`](docs/security-model.md). What an ordinary frontend change can break:

- **Anything running in the webview holds the full cluster surface, and the shell behind it.** `graphql_query` forwards the operation string unexamined, so a dependency that executes is a dependency that can read every mirrored object and call every mutation — `approvalDecide` included, which runs whatever command the model asked for. The CSP in `src-tauri/tauri.conf.json` is the containment — never widen `script-src`/`connect-src` to a remote origin, and never load a script the bundle doesn't ship.
- **The approval request is the user's eye, and the eye is the whole gate.** The request (`ApprovalRequest` in `chat-transcript.tsx`) draws the command as text, exactly what the shell will receive, or the path a read will open, or the path a write will change and every byte it will put there, or the path an edit will change and the two strings it swaps, or the URL a fetch will open and the host it dials, or the name and text a save for every cluster will keep, or the name a forget for every cluster will remove, or the method, path, media type and body a sandboxed command sends to change the cluster, with every invisible or reordering character spelled out and a long command or content folded behind a button Approve waits on — all but the command under a cluster write's *Sent by*, which is context — and Approve is a click on that request and nothing else: no keyboard shortcut, no default button, no "always allow", no approving from anywhere the command is not shown. Adding any of those is a security change under [the bash tool record](docs/security/2026-09-18-bash-tool.md). **Two calls run without a request**: a command the sandbox confines, and a `Write` or `Edit` in the chat's workspace, since the sandbox and the workspace's root are their bound → [Bash runs in a sandbox](docs/security/2026-09-28-bash-runs-in-a-sandbox.md). Each change such a command sends to the cluster is a request of its own → [cluster writes ask](docs/security/2026-09-29-cluster-writes-ask.md). A subagent's request is the same request, opening with *An agent asks:* and its `Agent` call's description, since the user is approving a call whose reasoning they cannot see → [the Agent tool](docs/security/2026-09-25-agent-tool.md). **An agent's requests wait whether or not an answer is streaming, several at once and under an answer that has settled**: every one is drawn, in the order asked; its buttons are live on a `Pending` approval while the message's `awaitingApproval` holds; and Approve arms only once its place on screen has held for `APPROVE_ARM_MS` (500ms), re-arming on any move, since the page moves around a waiting request and a click aimed elsewhere must not land on an Approve that slid under the pointer. The composer's *Show* and the chat list's dot point to a request out of view and never approve one → [background agents](docs/security/2026-09-25-background-agents.md).
- **The model's description of a command is its claim, never the app's.** It rides above the command on the request and under it in the transcript, and it is cluster data at one remove: one line, spelled through `VisibleText`, italic and quoted, labelled *The model says:* on the request, never in place of the command and never brighter than it. → [the command description](docs/security/2026-09-23-the-command-description.md).
- **Cluster data is attacker-controlled text.** Names, labels, annotations and event messages come from whoever controls the cluster. `src/` has no HTML sink — no `innerHTML`, no `dangerouslySetInnerHTML`, no `eval` — and the `custom/cluster-data-is-text` config object in `eslint.config.ts` fails the lint on one. Printer columns go through the restricted reader in `src/lib/jsonpath.ts`; the same config object refuses a template engine, by import and by call.
- **A chat answer inherits this.** The model has read the cluster, so its text is cluster data at one remove: `markdown.tsx` renders it to React elements with raw HTML left as text, and no rehype plugin may put HTML back.
- **The log-tail and exec windows inherit this.** When they land, treat their output as untrusted bytes: no HTML interpretation, and strip terminal control sequences.

## Frontend (`src/`)

React 19 + TanStack Router + [urql] (GraphQL) + Vite + Tailwind v4. UI primitives from `@kubetail/ui`. Package manager is **pnpm**. Path alias: **`@/*` → `src/*`**.

### Routing & layout

- Entry: `src/main.tsx` → `RouterProvider`. Routes in `src/routes/` (code-based, wired in `src/routeTree.ts`): `__root.tsx` mounts the provider stack; `_app.tsx` is a pathless layout route rendering `AppLayout` (the window shell); `chat.tsx`, `chat-id.tsx` and `dashboard.tsx` nest under it as peer routes. `index.tsx` (`/`) just redirects to `DEFAULT_ROUTE`. **A chat is a route, so each window can be in a different one**: `chat-id.tsx` is `/chat/$chatId`, `chat.tsx` the bare `/chat` a chat starts from. The id is a path param, not a search param — `retainSearchParams` on `_app` would otherwise drag it into the dashboard. The Chat/Dashboard switch is the sidebar's `ModeNav` (router `Link`s), so each mode is a real, deep-linkable route.
- **Layouts** live in `src/layouts/` — presentational shells rendering an `Outlet`. Secondary windows (log tail, exec) will get their own sidebar-less layout under a separate pathless route; a Tauri window opens at that route's path.
- App-wide concerns live in `src/lib/` (auth, error bus, sync-status, kube-config, ready-gate, `platform.ts`, `host-file.ts`, `theme.tsx`); reusable UI in `src/components/widgets/`.
- **`ReadyGate` (`src/lib/ready-gate.tsx`) draws `AppMark`** (`components/widgets/app-mark.tsx`, the lettered square `AppLogo` also renders) at 48px, centred, in every state — pending is the mark alone with `Starting…` as `sr-only` text, error keeps it above the message and Retry. `index.html` carries a static copy of the same mark inside `#root`, so the window shows it from the first paint and React's first commit replaces one with the other without anything moving.

### Errors reach the host's log

`src/lib/error-bus.ts` is the one producer of runtime errors (`reportError`), and `src/lib/error-log.ts` is the sink: `startErrorLogForwarder` subscribes to the bus and invokes the host's `log_webview` command with each record, and `installGlobalErrorHandlers` reports `error` and `unhandledrejection` as source `render`. Both are called from `main.tsx` **before `createRoot`** — a startup failure (`ready-gate.tsx` reports source `network`) or an `ErrorBoundary` crash happens above anything a component could reach. A module that throws while loading is not covered.

An `AppError` carries `source`, `message`, an optional `cause`, `componentStack` (the boundary alone fills it) and `context` — **explicitly chosen keys, never a serialized `cause`**: a `CombinedError` holds GraphQL payloads full of cluster text, so a producer that wants a detail names it. The forwarder reads `stack`, `componentStack` and `context` each under its own guard (a getter on an arbitrary `cause` can throw), caps every string, swallows a rejected invoke, and **never calls `reportError` on failure** — that would feed the bus back into itself. Sends past `MAX_IN_FLIGHT` are dropped, with `RESERVED_IN_FLIGHT` slots only `render`/`auth` may take, and the drop count rides as `context.dropped` on the next record that goes. The host re-applies its own caps and rate limits; it is the authority on what reaches the file (`src-tauri/CLAUDE.md`, Logging).

### Window-scoped state = URL search params

`kubeContext`, `resource` and `chat` (all on `_app`, kept across mode switches via `retainSearchParams`, so chat and back returns to the resource you left) are search params — per-window, deep-linkable, history-pushing. → [ADR: URL params as window state](docs/adr/2026-08-09-url-params-as-window-state.md). Accessors: `useActiveKubeContext` (`src/lib/active-kube-context.tsx`; falls back to the kubeconfig current context; `setContext` writes the param — a frontend view-scope only, never rewrites the kubeconfig) and `resolveDashboardResource`; `chat` is the dashboard panel's open chat, read by `DashboardChat` alone — it rides into `/chat/...` URLs, where nothing reads it and where it cannot be confused with the route's own `$chatId`. **The cluster is the window's one scope** — `kubeContext` names it, and everything else in the window follows from it. → [ADR: the cluster is the app's scope](docs/adr/2026-09-11-the-cluster-is-the-apps-scope.md). Links writing one param must spread the previous search (`(prev) => ({ ...prev, resource })`).

**The window is a column over a row** (`layouts/app-layout.tsx`, the one place the shape is expressed): the 56px **app bar** (`components/widgets/app-bar.tsx`), then a row holding the floating **left sidebar** (`left-sidebar.tsx`) beside `<main>`. Every band is an ordinary flex item — nothing is fixed-positioned — so the sidebar and the page start below the chrome by construction, with no offsets to keep in sync. The app bar is the window's title bar on every platform and is a `deep` drag region, so every pixel of it moves the window — spacing and margins included — while Tauri's hit test stops at the first clickable element, which is what keeps the buttons in it clicking (the omnibox opts out with `data-tauri-drag-region="false"`, being a control). Only its ends differ — macOS reserves the native traffic lights (the host centers them in it: `window_manager.rs` mirrors the 56), while the frameless platforms get `AppMenu` on the left and `WindowControls` on the right. The bar is the one place that decides: neither component checks the platform, and not mounting `AppMenu` on macOS is what keeps its `Ctrl/Cmd+N`/`Q` accelerators from firing beside the native menu item's. The **`HomeButton`** (`home-button.tsx`, links to `/chat`) and the back/forward **`HistoryNav`** (`history-nav.tsx`, an outlined group of two ghost buttons) follow whichever of the two is there — 16px from it, 8px from each other, both spacings set by the bar. At the far end, past the omnibox, sit the **`SettingsButton`** (`settings-button.tsx`, which only asks `AppDialogs` to open) and the **`SignInButton`** (`signin-button.tsx`) — a sign-in button while the session is absent, an avatar menu (Account, Sign out) once it is there; the pair sits 20px from the window's edge and 8px apart, both spacings set by the bar. Account is a web page, so the item invokes the host's `open_account_url` — the command names the URL itself, since a command that opened whatever the webview handed it would be an exfiltration channel. The bar keeps no padding of its own: the close button has to reach the window's corner. `AppLayout` also mounts the library's `SidebarProvider`, which owns `Cmd/Ctrl+B` and the narrow-window state; open/collapsed is controlled from the layout through `usePersistedFlag`, since the library persists it to a `sidebar_state` cookie it never reads back; `LeftSidebar` reads it through `useSidebar` and mounts one of two shapes: the open **`LeftSidebarCard`** (`left-sidebar-card.tsx`, drag-resizable, width in localStorage) or the collapsed **`LeftSidebarPill`** (`left-sidebar-pill.tsx`) — a narrow vertical pill in the same `p-2` footprint, so collapsing changes the sidebar's width and nothing else about the row. The card is a fixed top over a scroller: its `SidebarHeader` opens with a row carrying the app's mark on the left and the **sidebar toggle** (`left-sidebar-toggle.tsx`) on the right, then whatever the layout pins under it — `ModeNav`, since it is how you leave whatever the nav below is showing — and its `p-2` is the padding above and either side of the card's contents; `SidebarContent` scrolls beneath it, padded to match but flush with the bottom edge. The toggle rides the pill too, beside the mode switch as icons (router links, like `ModeNav`), so a collapse is reversible without `Cmd/Ctrl+B`. Too narrow for the card beside the page there is only the pill, and the toggle opens the card over it as a drawer. **Narrowness is the provider's own `isMobile`** (its hardcoded 768px), never a second media query: `toggleSidebar` branches on it to flip either `open` or `openMobile`, so a component rendering off a different rule leaves that button flipping a state nothing shows — which is exactly the bug a private `useIsNarrow` caused. `openMobile` starts closed, so narrowing collapses rather than throwing a panel over the page, and widening restores `open` untouched. The pill keeps the row's width so the page never shifts under the pointer, and the card is absolutely positioned over the content row, which `app-layout.tsx` makes `relative` for it. A scrim, Escape, or any navigation from inside closes it, the last because a drawer left open covers the page it just opened. It is `role="dialog" aria-modal`, held by **`useFocusTrap`** (`src/lib/focus-trap.ts`): Tab stays inside it and focus returns to the toggle on close, since a panel that covers the page must hold the keyboard as well as the eye. Both yield to an overlay opened from inside the drawer (the chat list's delete confirm): the trap stands aside while its own node sits under an `aria-hidden="true"` element — what an overlay library marks the outside with when it takes over — and the drawer's Escape listener stays on `window`, later in the bubble path than the `document` listener a dialog dismisses on, so one keypress closes the dialog alone.

The **right sidebar** (`right-sidebar.tsx`) is the row's last item — flush against the app bar and the window's bottom edge, taking its width from the page rather than covering it, which is what separates it from the floating card on the left. It is drag-resizable from its inner edge (240–640px, remembered under its own key) — the handle and the clamped, persisted width are shared with the left card as **`ResizeHandle`** (`resize-handle.tsx`, whose `edge` decides whether the pointer's x or what is left of the window is the width) and **`usePersistedWidth`** (`src/lib/persisted-width.ts`). It opens from `RightSidebarToggle`, which `AppLayout` pins to the content row's top-right corner rather than to the page — so it holds its place as the panel opens under it, over the page while closed and over the panel once open, and below the left drawer's scrim so a covered control cannot be clicked. What the panel holds follows the mode: the dashboard's is `DashboardChat`, chat mode's still a placeholder (the conversation's metadata — logs, graphs, whatever the answer refers to). **The `aside` does not scroll** — its contents own a scroller each (the recent list, or the transcript), and one inside another gives two scrollbars that fight. Its state is `useRightSidebar` (`src/lib/right-sidebar.tsx`), mounted around the row since the toggle and the panel are siblings there: out of the URL, because it is chrome rather than what the window is looking at, and persisted app-wide beside the width (`usePersistedFlag`, `src/lib/persisted-flag.ts`) — and **per mode**, open state and width alike, since the two panels hold different things. The layout supplies the mode rather than the provider reading the route, so the panel and its toggle cannot disagree about which one they answer for; the width follows through the storage key, and `usePersistedWidth` re-reads when that key changes so a mode switch does not carry the other's width across.

The **context omnibox** (`context-omnibox.tsx`) rides the app bar's centre, between two spacers that keep 16px each however narrow the window gets, so it sits in whatever the two ends leave. It shares that slack with them rather than holding a fixed width — its wrapper starts at the omnibox's own 416px and grows a third of what is left, up to the 640px cap the omnibox itself sets — and the cluster value `truncate`s under pressure, which needs `shrink` on its trigger because the library's button base pins `shrink-0`. It holds: a clusters-dialog icon, then the cluster in view, a quick dropdown over the state the clusters dialog writes, then the **`MemoryButton`**, a brain icon that opens the `memories` dialog and is lit (`data-lit`) while the cluster sees any memory. The "Unverified TLS" badge rides beside the cluster segment, the one place the app says a connection goes unverified. `HistoryNav` walks router history via `__TSR_index` read through `useSyncExternalStore`.

**The sidecar mirrors the kubeconfig and draws no verdicts over it.** `status.source.kubeconfig.cluster` is `{ name, entry }` — the name the context references, and the entry the file defines under it (`server`, `insecureSkipTLSVerify`; null when there is none). `user` is the name alone: an authInfo entry holds credentials, so anything served from it is a projection, never a mirror, and `tlsUnverifiedReason` in `src/lib/kube-config.tsx` is the one place that turns it into the omnibox's badge — a second inline copy is how the plain-`http` arm goes missing, and no sidecar test would catch it. → [ADR: status mirrors the kubeconfig](docs/adr/2026-09-03-status-mirrors-the-kubeconfig.md).

### Dashboard resource nav

The curated base tree is `DASHBOARD_NAV` (`src/lib/dashboard-resources.ts`); `buildDashboardNav(serverKinds)` merges in the active cache's discovered kinds (bucketed by API group; unmapped groups — including core — deferred to Custom Resources work). Disclosure style is derived from shape (curated `children` vs discovered `moreChildren`); counts join by API group + plural via `CURATED_LEAF_API_GROUP`. `DashboardResource` is an **open string**, validated leniently. → [ADR: dashboard nav merge](docs/adr/2026-08-09-dashboard-nav-merge.md).

Live data: `useClusterCachedDataKinds` (`src/lib/cluster-cached-data-kinds.tsx`) consumes the `clusterCachedDataKindsWatch(id, cacheID)` subscription; `useDashboardNav` builds the tree over it. All three cached-data hooks resolve the active cluster/cache through the shared `useActiveCluster()` (`src/lib/active-cluster.tsx`) and reduce through the shared **`useCacheDeltaWatch`** (`src/lib/graphql/use-cache-delta-watch.ts`), which owns the id-keyed fold, the **cache/kind provenance guard** (rejects retained rows and stragglers from a superseded cache — don't bypass it; → delta-watch ADR), and `watchPhase`. `AppLayout` mounts `DashboardResourceNav` (`components/widgets/dashboard-resource-nav.tsx`) in the sidebar only while `/dashboard` matches (`useLocation`, which re-renders per navigation); `routes/dashboard.tsx` reads `resource` back and picks a panel three ways: `events` → `EventsTable` (`events-table.tsx`, fed by `useClusterCachedDataEvents`), a resolved discovered kind → the generic `ObjectsTable` (`objects-table.tsx`, fed by `useClusterCachedDataObjects(kind)` — keyed by cache **plus** `apiVersion`+`resource`), else a placeholder. `ClusterCachedDataObject.rawJSON` is the full native body (typed `unknown`). Kind-specific columns are two-tier (`object-columns.tsx`): a hand-written registry entry wins — it says what a jsonPath cannot — else the kind's own `printerColumns` off the kinds watch, evaluated against `rawJSON` by the restricted reader in `src/lib/jsonpath.ts`. Only Pod and Deployment are hand-written; the other built-ins are the remaining step, see `docs/TODO.md`. Both tables gate on the same `active`/`phase` split (no active cache → "not synced", `connecting` → spinner, then `live` with no rows → "No …").

**Both tables render through `VirtualTable`** (`components/widgets/virtual-table.tsx`): only the rows on screen are in the DOM, as real `<tr>`s between two spacer rows. The whole technique rests on two facts. **Every row is `ROW_H` tall** — the class is applied to every row and `ROW_H_PX` is the matching number, *read off a rendered row* (`TableRow` has `border-b` under collapsed table borders, so it is not `h-9` arithmetic); a wrong constant drifts rows out of position further down a long list. **The table is `table-fixed`**, so column widths come from the always-present header, not from whichever rows happen to be rendered; a column's `className` carries its width (`object-columns.tsx` gives every registry and descriptor column one), the free-text columns (Name, Message, Object) `truncate` with a `title`, and an unsized column takes the slack. A `VirtualColumn` has `ObjectColumn`'s exact shape, so the objects table concatenates its columns with `columnsForKind(...)`.

**The rows are a live watch, so they shift index under the scroll offset on every frame.** After each commit the table remembers the rows on screen; on the next it moves `scrollTop` by the *smallest* shift any surviving one made — rows the user is reading move together when something is inserted or removed above them, and a row that moved on its own (an event re-fired to index 0 of the newest-first list) is the outlier. Within one row of the top it does nothing, so new rows arrive in view like a log tail. The scroller sets `overflow-anchor: none`: Chromium (Windows) would stack its own anchoring on the correction; WebKit (macOS/Linux) has none, which is why the component owns it. The scroller is `tabIndex={0}` so Home/End/PageUp/PageDown work — the browser's own behaviour on a focused overflow container.

**The layout bounds the scroll.** A scroller needs a definite height, so the chain is `h-(--app-min-h) min-h-0` on the `SidebarProvider` column, then `min-h-0 flex-1` on the content row, then `min-h-0 flex-1 overflow-hidden` on `<main>` (all three in `app-layout.tsx`), then `flex min-h-0 flex-1 flex-col` on the route's `<section>`, then the table's `flex-1 overflow-auto`. `min-h-0` goes on every *plain* flex item between the frame and the scroller (a flex item's minimum is its content, so without it the section grows to the spacer rows and `<main>` clips it) and never on the scroller itself (a scroll container's minimum is already zero). It must also stay beside `h-` on the provider — the library hardcodes `min-h-svh`, which only `min-h-*` displaces via tailwind-merge; on Linux `--app-min-h` is `100%` of the `WindowFrame` inset, shorter than `100svh`, so a leftover `min-h-svh` would make the chain taller than the frame. That percentage is definite only while every DOM ancestor is — one wrapper `<div>` between `WindowFrame` and the provider breaks it. Any other route under `_app` that scrolls needs `min-h-0` on its own chain (`chat.tsx` via `CenteredColumn`). Tests that render rows call `stubLayout()` from `@/test-utils` — jsdom has no layout, so without it a virtualized table renders none.

### Chat

**A chat is drawn in two places, and `chat-pane.tsx` holds the two panes both mount**: `ChatPane` is one chat (transcript over composer), `NewChatPane` a chat that has not started (its `empty` slot over a composer). Chat mode's page and the dashboard's right-sidebar panel mount them. Neither navigates: `NewChatPane` reports `onCreated(id)` and `ChatPane` reports `onGone()`, and the home decides where the window goes — `chat.tsx` navigates to `/chat/$chatId` with `replace: true`, `chat-id.tsx` back to `/chat`, `DashboardChat` writes or clears its `chat` param.

**Reads are `src/lib/chats.tsx`**: `useChats` (the recent list, sorted by `Date.parse(updatedAt)` desc then `id` desc — `Time` is an ISO string on the wire, and the stored millis really do tie) and `useChatMessages(chatId)` (ordered by `seq` — the transcript's order, a counter the sidecar assigns; ids are opaque and order nothing), both `unshared: true` because a consumer can mount into a stream already running. Both fold an id-keyed map with a `synced` flag straight over `useWatchSubscription` — no `useCacheDeltaWatch`, since there is no cache provenance to guard — keyed on `type === 'Bookmark'`, never on a missing entity. `textOf` is the one reader of a message's text blocks: `content` is `JSON!`, so it arrives `unknown`, and a second, laxer copy of that narrowing is how a tool block ends up on screen. **A tool round draws nothing** — an answer's `tool_use` and `tool_result` blocks are skipped like thinking — but two text blocks with a round between them were written at different moments, so `textOf` puts a blank line between them; drawing the rounds themselves is a follow-on. **A server call is a moment boundary too**: a `server_use` block — one call of a tool the provider ran, kept in the content for the replay in a `tool_use`'s fields — separates text the same way, whatever it holds. What a search asked is its **row**, not its block: `searchesOf(toolCalls)` is the one reader of the searches, `{ count, queries }` over every call of the answer's own (no `agentCallID`) that `ranSearch` passes — a `Search` by `actionKind`, the provider's or the sidecar's once `Succeeded` — the queries off `action.search`, empty ones left out, so a search whose arguments did not parse counts and lists nothing (`actionKind` is the tool's, read through the sidecar's box, never from the arguments; a call's `name` is the tool's name in the box and its `contract` the vendor's own identifier for the shape it uses), and `sourcesOf(citations)` the one reader of `ChatMessage.citations`, which the sidecar reads from the provider's payloads by the dialect of the run that wrote them — one entry per URL, in citing order, the first title winning, a citation with no URL (a document the model was given) left out. All of it is web text, read as data and drawn as text. **A question may carry a `context` block** — the cluster card the sidecar attached, what the model was told about the cluster on that turn — which `textOf` ignores and `contextOf` beside it reads. `chatModeOf` is the one mapping from `AppMode` (`src/lib/app-mode.ts`) to the wire's spelling, so the list filter and the send agree. **A chat belongs to one mode and one cluster, both stored** (`Chat.mode` and `Chat.clusterID`, fixed at creation), so each list shows only its own mode and cluster. **A chat can switch to any model**: any send may name any model in the catalog, whichever provider wrote the answers before it (→ [ADR: a chat can switch to any model](docs/adr/2026-09-25-a-chat-can-switch-to-any-model.md)). Both list filters are the client's: the watch is unscoped, since `OpenChat` has to tell a deleted chat from one of another cluster.

**Writes are `src/lib/chat-outbox.tsx`**: one entry per chat holding the draft, the model and effort it is set to send at, and the send in flight, keyed by chat id or `new:<mode>` for the chat that has not started. The provider sits at `AppLayout`, above the routes, because the composer unmounts under it — the first send moves chat mode to the new chat's route, a chat deleted elsewhere takes its pane down — and a send must settle into its entry whatever became of the box that started it. `useChatOutbox(mode, chatId, clusterId?, seed?)` is the whole API: `draft`/`setDraft`, `pick`/`setPick`, `send`, `submit`, `retry`, `discard`, `askAgain`, `settle`, and `moveDraft` for the one time a draft changes chats (the deleted-chat notice's "Start a new one", which joins it onto whatever is waiting at the unstarted chat). **Nothing else moves between keys.** A send settles into the key it left from: an existing chat's goes `awaiting(seq)` until the messages watch delivers that row, and the composer — the only thing watching those messages — calls `settle(last.seq)` to close it, so the entry is idle again for whatever the window sends next, Ask again included; a created chat's leaves the unstarted entry idle and empty, since the route it opens delivers the row with its snapshot and the unstarted key watches no messages that could settle an `awaiting`.

**What a send runs on is the entry's too.** `pick` is a model and an effort; an entry not yet picked for takes the `seed` the composer computes — the chat's last answer, or the catalog's first model — read only once both the messages watch's `Bookmark` and the catalog have answered, since before either there is nothing to seed from. **The effort belongs to the model that ran it**: falling back to another model takes *that* model's default, never a level it happens to spell the same. `useModels` (`src/lib/models.tsx`) is the one reader of the `models` query and owns `seedPick`/`modelOf`; it separates a sidecar that answered with nothing (no key — Send is disabled and the placeholder says so) from one that could not be reached (`failed`, with `retry`), and the composer asks again **once per live watch** (`useAskAgainWhenLive`, `src/lib/ask-again-when-live.ts`), since a query re-runs for nobody and asking on every failure is a request loop.

**A failed answer can be asked again by hand.** The sidecar never retries a turn, but a 429 or a socket dropped three tokens in is a row, not a refusal — the send was accepted and the draft is gone. So the transcript's **last** row, when it is a `Failed` answer, draws **Ask again**: `askAgain(content, pick)` on the outbox, a fresh send under a new `requestID` carrying the question the failed answer followed and what that row ran on. It rides the entry's one send, so a press while anything is in flight sends nothing, and **it leaves the draft alone** where `submit` clears it — what `submit` sends is the draft, what this sends came off the failed row. The name is not Retry: the composer's Retry is the same send under the same `requestID`, answered by the key on the message it wrote.

**A background command outlives its answer.** A bash call with `run_in_background` that asks says so on its approval request — *Run this command in the background?*, or *Run this command in the background, outside the sandbox?* — with *It keeps running after this answer, until it exits or you stop it.* under it (`action.command.background`). Its call's disclosure tags off `ToolCall.background` — `running in background`, `exit N`, `stopped` or `lost` — and while it runs a **Stop** button under it calls `backgroundTaskStop(id)`: down from the press, still down on a `false` answer (the watch takes it away), handed back only on an error. A Cancel stops the answer, not the commands it started. **A command's end reaches the model as a notice on a user message** — on the next question, or, for an exit, on a message of its own that starts a turn. `noticesOf` in `chats.tsx` is the one reader of a notice block, and `textOf` ignores it. A notice is never a bubble: one muted line — *Background command finished · exit 0*, *stopped*, or *lost when Kstack stopped*, with *· started by an agent* when a subagent's call started it (`TaskNotice.agentDescription`); for an agent's notice (`TaskNotice.kind`), *Agent finished*, *Agent failed*, *Agent stopped*, *Agent stopped: no answer in 30 minutes* or *Agent lost when Kstack stopped* — then the task by the model's description through `ModelDescription`, else a command's text through `VisibleText`. An agent's report and error ride the notice for the model; the line draws neither. A message of notices alone draws its lines alone; a question they rode draws them above its bubble. **A failed answer to notices alone draws no Ask again**, since there is no question to ask. → [security record: background commands](docs/security/2026-09-23-background-commands.md).

**An `Agent` call holds its subagent's calls.** The model can hand a task to a subagent, which runs in the background: the call answers at once, and the agent is a background task of the chat like a command, its end a notice. The subagent's calls arrive in the answer's `toolCalls` after its own, each with `agentCallID`, the `Agent` call it ran under (null on the answer's own), whether the answer is still going or has settled. The top level draws the answer's own calls alone. The `Agent` call is a disclosure like any other, its summary *Agent* and the model's description under it, tagged off `ToolCall.background` as a command's is — `running in background`, `completed`, `failed`, `stopped` or `lost` — with a **Stop** under it while it runs, and its body opens with a muted line naming the type and, when the call named one, the model by its catalog label, then the brief (`action.delegate.prompt`) through `VisibleText`, folded by `cutText`, then the subagent's calls as disclosures of their own, then the report (`background.report`, cut by the sidecar to the inline limit) through `Markdown` — nothing until it completes. The call's `output` is the launch text the model read, and is not drawn. A subagent's call awaiting approval is the one exception: it is the request, found among all of the answer's calls and drawn where a request is drawn, never inside the disclosure. → [security records: the Agent tool](docs/security/2026-09-25-agent-tool.md), [background agents](docs/security/2026-09-25-background-agents.md).

**A send refused with `KSTACK_CHAT_CONTEXT_FULL`** — the chat is longer than the model it named can read — settles to `idle` with the draft kept, like any refusal, and is the one refusal the entry remembers: `refusal: { kind: 'context-full', model }` — the model *that send* named, since the pick can move on and an Ask again runs on the failed row's — cleared by the next send whichever model it names. The composer draws it as one line above the box naming that model (`This chat is longer than Claude Haiku 4.5 can read. Pick a model that reads more, or start a new chat.`); Send stays enabled, since another model may take it. A failed answer whose row says `chat is longer than the model can read` is the sidecar's own overflow, and its Ask again is refused the same way. **A send refused with `KSTACK_CHAT_SANDBOX_CHANGED`** is remembered the same way, as `{ kind: 'sandbox-changed' }`, and drawn as *This chat's sandbox switch changed. Check it, then send again.*

**A command in a chat the user switched outside the sandbox stops the turn on the user**, and the transcript draws it as the **approval request**; one the sandbox confines runs unasked. The model cannot leave the sandbox: only the user's switch does (→ [security record: outside the sandbox is the user's choice](docs/security/2026-09-30-outside-the-sandbox-is-the-users-choice.md)). The sidecar offers bash where it finds a shell, and `Read`, `Memory`, `Write`, `Edit`, `WebFetch` and `KubeQuery` on every machine, to every turn on a model that takes tools; KubeQuery asks no one. **A command starts in the chat's workspace**, `workspace/` in the chat's own directory, unless its `workdir` names another directory, so the request's `in <dir>` line names the workspace for a call that names none; `Write` and `Edit` reach the workspace and nothing else under Kstack's directories, and run there unasked. `ChatMessage.toolCalls` lists every call of a turn off its row — what the model read as `output`; the call's `action`, read from its arguments by its own tool in the sidecar (the webview parses no tool's arguments and does not select them): the model's `description` (`''` when it gave none) and one kind, a `command` (the exact command as `text`, the directory it runs in as `cwd` — `''` for a call that never reached the gate — `background`, and `sandboxed`, off the row: whether a sandbox confined it), a `read` (`path`), a `write` (`path` and `content`), an `edit` (`path`, `oldString`, `newString` and `replaceAll`) a `fetch` (`url`, upgraded to https with its host in ASCII, and `host`, the host it dials) a `memory` (`op`, `name`, on a save the note's `body`, and `scope`, `cluster` or `everywhere`) or a `kubeQuery` (`sql`, the statement as it runs, and `limit`), and null when the tool cannot show the call; and on a gated call its `approval`: the `id` to decide while the call is `AwaitingApproval`, and the decision as `status`, so a call approved and never started reads `NotRun` beside an `Approved` approval. `useChatMessages` selects it and `ChatToolCall` is its type. Under an answer's text, `ChatTranscript` lists every call of the answer's own not awaiting approval that `ranSearch` does not pass as a closed disclosure, the provider's included, since it left the machine — a search that ran is drawn under *Searched the web* alone, a plain line when it has no query to list — its summary spelled through `VisibleText` with no `title` so an override cannot reorder the tag beside it. **`summaryOf` is the one reader of a call's summary**: `action.command.text`, so a command that never reached the gate reads as its text beside its `not run` tag; else `Read <action.read.path>` (a read of the chat's saved files, its workspace included, asks no one; any other file is asked for, like a command); else `Write <action.write.path>`, its body the content folded as on the request, then the result; else `Edit <action.edit.path>`, its body the two strings drawn as on the request, then the result — **except a `Write` or `Edit` with no `approval` that `Succeeded`**, a write in the workspace nobody was asked about, whose content or strings are drawn open under the summary instead, outside the closed disclosure and not again inside it, since a later command may run the file; else `Fetch <action.fetch.url>`; else `Save memory <name>` or `Forget memory <name>` off `action.memory`, a save that succeeded holding the body it kept through `VisibleText`, and a save that did not, no body, and a call for every cluster carrying a muted *for every cluster* after the name whatever its status, so a denied one never reads as a call for the cluster; else `Search <action.search.query>` (`Search` for an empty query: a sidecar search that did not run); else the kind through `actionKindLabel`, the one spelling of a kind (arguments the tool refuses, and every TaskStop, which reads *Stop task*, a fetch's *Fetch page*, an Agent call's *Agent*, and a KubeQuery call's *Query*, its body opening with the SQL through `FoldedBlock`, mono, above what the model read); else the tool's name, the description under it, a body opening with the `in <dir>` line above what the model read — `in <dir>, sandboxed` for a call whose `sandboxed` is set, the `, sandboxed` muted and outside the directory's `VisibleText`, while the request never says it — a tag off the status alone (`toolCallTag`: a `Failed` call's first line is the sidecar's `Exit code N` or `Command timed out …`, read alone since the output starts on the next). Each call awaiting approval is an `ApprovalRequest` — the answer's own, and each of its agents', drawn after the answer's text and calls in the order they were asked (`waitingRequestsOf` in `chats.tsx`, by `approval.id`, a UUIDv7, the one reader the composer's Show uses too), each with the DOM id `approvalAnchor(approval.id)` — drawn from its `action`: *Run this command?* (*Run this command in the background?* for a background one), or *Run this command outside the sandbox?* (*Run this command in the background, outside the sandbox?*) unless the machine has no sandbox (`commandHeading`, off the `sandboxAvailable` `OpenChat` hands `ChatTranscript`): there only a command outside the sandbox asks, and while the query has not answered the outside heading is still true. It never follows the chat's switch, which the user can flip while a request waits on a turn that read it, then the description line, then the command through `VisibleText` (`src/lib/visible-text.ts`: `visibleSegments` spells every invisible or reordering character out in a `<mark>`, `cutText` folds past 2,000 characters or 24 lines behind *Show the rest*, and Approve waits on it), wrapping anywhere with no height cap, then *Show the rest* when folded, then **the directory line** (`WorkingDirectory`: a muted `in`, then the directory in mono through `VisibleText`, `break-all`, never folded or cut, and no line for an empty `cwd`) — always under the command, never above it — then Approve and Deny, which call `approvalDecide(id, approve)`. **A read's request is *Read this file?*** — then the path in mono through `VisibleText`, `break-all`, never folded, since `fileguard.Abs` refuses one with a control character or past 4,096 bytes, with no description line (Read's schema has none) and no directory line — then Approve and Deny as for a command. **A write's request is *Write this file?*** — then the path as a read's is, then the content through `VisibleText`, folded by `cutText` behind *Show the rest* with Approve waiting on it, so a CRLF content marks every `\r`; `visibleSegments`' `trailing` mode spells each space or tab that ends a line (the fold's head ends a line only where the fold falls on a newline), and a muted line under it says *Ends with a newline.* or *No newline at the end.* — none of which a `<pre>` draws — and *The file will be empty.* for none. The field is read through `writeOf`, since the HTML-sink lint refuses any `.write`. **An edit's request is *Edit this file?*** — then the path as a write's is, *Every occurrence in the file.* when `replaceAll` is set, then *Replace* over the old string and *With* over the new (`EditBlocks`), each drawn as a write's content is and folded on its own, Approve waiting on both, and under each a line naming its edges — *Starts and ends with a newline.*, *Starts with a newline.*, *Ends with a newline.* or *No newline at either end.* — since a newline at either end joins or splits lines and a `<pre>` draws neither; an empty new string reads *The text will be deleted.*, and two strings equal with every `\s` removed carry *The two differ only in whitespace.* The strings are drawn as the model sent them, never as a diff. **A fetch's request is *Fetch this page?*** — then the URL in mono through `VisibleText`, `break-all`, never folded, since the sidecar caps it at 8,192 bytes, then a muted `Host:` line with `action.fetch.host` in mono through `VisibleText`: the host the sidecar dials, drawn off the action and never parsed in the webview, on a line of its own since a long URL can hide it — then Approve and Deny. **A save for every cluster's request is *Remember this for every cluster?*** — then the name in mono through `VisibleText`, `break-all`, never folded, since `memorysvc`'s shape check has passed before any request exists, then the body as a write's content is, folded with Approve waiting on it and each space or tab ending a line spelled, with no line about how it ends, then a muted *Kstack will read it in every cluster's chats.* — then Approve and Deny. **A forget for every cluster's is *Forget this memory for every cluster?*** — then the name as a save's is, and no body, since a forget carries none — then Approve and Deny. **A cluster write a sandboxed command sends is a request too.** `ToolCall.clusterWrites` lists every one the call's command sent, in the order asked, each with its `approval`, `method`, `path` (with its query, as sent), `subresource` (the proxy's parse), `dryRun`, and, while it waits — `Pending` on a `Running` call — its `contentType` and `body`, empty once it no longer waits. `waitingRequestsOf` takes a waiting write as a request beside the calls', its `change` the write (null for a call's own), so it sorts by `approval.id` with them and the composer's *Show* and the chat list's dot find it. Its request reads *Create in the cluster?*, *Replace in the cluster?*, *Patch in the cluster?* or *Delete from the cluster?* by method, or *Change in the cluster?* for a write with a `subresource`, which the webview reads and never splits off the path, with *(dry run)* after it when `dryRun` is set; then the path in mono through `VisibleText`, `break-all`, never folded; then the method and, for a write with a body, its media type through `VisibleText`, since a subresource's heading names no method and the media type decides what a patch's body does (a merge patch replaces a list a strategic one merges); then the body as a write's content is, folded with Approve waiting on it, nothing for an empty body; then a muted *Sent by* and the call's command, folded, which Approve does not wait on, since it is context. A subagent's opens with *An agent asks:* like its other requests. A call's writes that no longer wait are lines of its disclosure, under its output: the method and the path through `VisibleText`, tagged `approved`, `denied` or `not answered` (`Abandoned`, or `Pending` on a call a crash stranded); `approved` is the decision, not that the cluster received it → [cluster writes ask](docs/security/2026-09-29-cluster-writes-ask.md). The group's `aria-label` names what waits: *Command awaiting approval*, *File read awaiting approval*, *File write awaiting approval*, *File edit awaiting approval*, *Page fetch awaiting approval*, *Memory save awaiting approval*, *Memory forget awaiting approval*, or *Cluster change awaiting approval*. A memory call for one cluster never waits on the user, so the request draws none. **A request with none of `action.command`, `action.read`, `action.write`, `action.edit` and `action.fetch`, and no `action.memory` whose `scope` is `everywhere`, offers no Approve** — one muted line, *This request can't be shown.*, and Deny — since a call that asks has an action the request can draw and what the user cannot see is not approved. **The description is one line wherever it is drawn**: `descriptionLine` (`src/lib/visible-text.ts`) is its one reader (the first line with anything on it, cut to 200 characters, `…` only when more than whitespace was cut) and `ModelDescription` its one drawing — italic, quoted, the text in a `truncate` span with the quotes outside it so the closing one survives the ellipsis, the color of wherever it sits (muted in the transcript, like the command above it), and no `title`, since a native tooltip draws the text unspelled. On the request it follows *The model says:*. **The buttons are live only on a `Pending` approval while the message's `awaitingApproval` holds** — true while any run of the answer waits on the user, its own or an agent's, which an agent's can under an answer that has settled; the row can still say `AwaitingApproval` a moment after the decision commits. **Approve also waits for its place to hold** (`useHeldStill`, `src/lib/held-still.ts`: the buttons' rect read every animation frame, unchanged for `APPROVE_ARM_MS`, 500ms, any move starting the wait again); Deny never does. `ChatTranscript` takes `approveArmMs` for its tests, and production passes nothing. A `false` answer leaves them down (no turn was waiting; the watch takes the request down), and only a mutation error hands them back. **The request is keyed on `approval.id`**, never the call or the message, so one request's pressed state never reaches the next. `WaitingApproval` is in flight like `Streaming` (`inFlight` in `chats.tsx` is the one test of that), so the answer draws the spinner and the composer refuses a send and shows Cancel. An agent waiting does not put its message in flight: the user may ask the next question meanwhile. → [security records: the bash tool](docs/security/2026-09-18-bash-tool.md), [bash offered to every turn](docs/security/2026-09-22-bash-offered-to-every-turn.md), [the command description](docs/security/2026-09-23-the-command-description.md), [the command names its directory](docs/security/2026-09-23-the-command-names-its-directory.md), [saved output and Read](docs/security/2026-09-23-saved-output-and-read.md), [the request reads the arguments](docs/security/2026-09-23-the-request-reads-the-arguments.md), [read any approved file](docs/security/2026-09-23-read-any-approved-file.md), [the write tool](docs/security/2026-09-24-write-tool.md), [the edit tool](docs/security/2026-09-24-edit-tool.md), [the web fetch tool](docs/security/2026-09-24-web-fetch-tool.md), [memory](docs/security/2026-09-24-memory.md), [KubeQuery reads the mirror](docs/security/2026-09-27-kubequery-reads-the-mirror.md), [Bash runs in a sandbox](docs/security/2026-09-28-bash-runs-in-a-sandbox.md).

**Memory is what a cluster's chats remember**: a name and a body, for that cluster or every cluster. Kstack saves the cluster's own as you talk, and one for every cluster once you approve it. A memory the user wrote is a request the model follows, one Kstack wrote is information (→ `sidecar/CLAUDE.md`). `useMemories(clusterID)` (`src/lib/memories.tsx`) folds `memoriesWatch` into an id-keyed map, gated on `type === 'Bookmark'`, `unshared` since the omnibox's button and the dialog both watch, and paused with no cluster; it lists the cluster's own first, then every cluster's, each by name — the order the model reads them in. **`MemoryDialog`** (`memory-dialog.tsx`, the `memories` app dialog) groups them under *This cluster* and *All clusters*: each row its name, date and *by you* or *by Kstack*, expanding to its body as plain text in `whitespace-pre-wrap`, never markdown, since the model may have written it from cluster data. The dialog adds, edits, renames and moves a memory through `memorySave`, and deletes one through `memoryDelete` once confirmed inline. **The form checks the shape itself**, since `KSTACK_VALIDATION_ERROR` names no field: a name breaking the pattern or past 48 characters, or a body past 500 bytes in UTF-8, draws its rule under the field and holds Save. **Saving one of Kstack's memories makes it the user's**, and the form says *Saving makes this your memory: Kstack will follow it.* under Save while it holds one. **One form at a time, held by the dialog above the list**: it fixes the memory as read and the cluster when it opens, so what the watch brings meanwhile leaves the draft alone, and neither a row leaving the list nor a reconnect's spinner drops it. It is locked while a save is in flight, and a refused save keeps the draft and says why by its code: a taken name, no room in the scope, a credential, a bad shape, or a memory or cluster gone. → [ADR: memory is rows](docs/adr/2026-09-24-memory-is-rows-scoped-to-a-cluster-or-every-cluster.md).

**`Send` is one value** — `idle | sending | held | awaiting` — so a held send cannot also be settled. The box is read-only while `sending` or `held`, so what is in flight is what it shows. **A refusal is settled, a dropped response is not**: a GraphQL error goes back to `idle` with the draft kept and the next submit mints a fresh `requestID`, while a `networkError` holds the id, the content, **the cluster it left with, the model and effort it was sent at, the sandbox switch it said, and whose text it was** behind Retry/Discard — a held Ask again is still not the draft's send, so its retry must not clear a follow-up typed since, since committed-but-lost is indistinguishable from never-arrived and the sidecar answers a repeat by its key alone — a retry is the same send, not a new one under whatever cluster the window has moved to. `submit` and `retry` resolve to the chat they created — its id and the cluster it was filed under — or null; that is all the composer acts on, and it follows one only while still mounted and still on that cluster, so a send that lands after the window moved on does not move it again. **The composer of a chat that has not started outlives a cluster switch**, so `mounted` alone would open the created chat under a cluster it does not belong to.

**`OpenChat` is keyed on the chat id** — one pane serves every chat, so without the key A's scroll position and watches carry into B. Both watches live in it, under the id rather than above, so a pane with nothing open opens neither. Absence is gated on the list's `Bookmark`; after it, an id the map does not hold renders "This chat was deleted." A chat deleted while a send is refused with `KSTACK_RECORD_NOT_FOUND` reaches the same notice through the list watch, since the sidecar streams every `Deleted`. **A chat of another cluster renders its own notice**, gated on the clusters snapshot the way absence is gated on the list's — before it every chat looks like another cluster's — and a deep link or Back can leave the window on one cluster with another's chat open — with a `Switch to it` button while that cluster is still a kube-context to switch to. There is no "Start a new one" beside it: the chat is still there, and a draft typed into it waits in its outbox entry until the window is back on its cluster. **Switching cluster from the omnibox leaves whichever chat the window is on**: it clears the `chat` param, so the dashboard panel returns to the new cluster's list, and from `/chat/$chatId` it navigates to `/chat`, since there the open chat is the route. The notice is for arriving at a chat of another cluster, never for stepping off one. `setContext` itself leaves both alone, because it is what that button calls.

`ChatComposer` (`chat-composer.tsx`) draws the box, and beside Send **two selects over the catalog**: the model, then its effort. The model select groups the catalog by provider, in catalog order, under each `provider.label` — and draws the headings only when there is more than one provider, since one needs none. **Every chat's select holds the whole catalog**, open or not yet started, and `seedPick` reads the same list. **A stored pick the catalog lacks is written back to the seed** by an effect — a model can leave the catalog, and the outbox outlives the composer — and `canSend` reads the entry's actual pick against the catalog, never a fallback computed in render, so Send is shut until the write-back lands; with nothing to seed the pick is left alone. A held send is not a pick: Retry sends what it holds. Changing the model resets the effort to the new model's default — the levels are the provider's own words — and a model with no such knob hides the second select. An empty catalog disables Send and the placeholder reads `Set an API key, then restart Kstack` — keys are read once at startup — but only once the query has answered, for the same reason the cluster placeholder waits. Enter sends, Shift+Enter is a newline, and Enter while an IME is composing confirms the character (`nativeEvent.isComposing`). Send is disabled while what the composer waits on is `connecting` — the messages watch for an open chat, the clusters watch for one that has not started — while the send is not settled, while a new chat has no cluster to be filed under (the placeholder then reads `Pick a cluster to start a chat`, but only once the clusters watch has answered: a window at startup has not failed to pick anything), and while the last message is `Streaming` — which also puts Cancel in Send's place; **`Streaming` is in the guard as well as behind the button**, since Enter goes through the same check and one turn per chat means the sidecar would refuse it. It reports nothing itself — `errorReportExchange` already forwards every operation error. **While a message before the last awaits approval**, the composer draws one line above the box, *An agent is waiting on you.*, and a **Show** that scrolls to the first request in it (`ChatPane` finds it and passes `onShowWaiting`): the transcript follows the last message down by itself, never an earlier one. Show scrolls; it never approves.

**The composer holds the chat's sandbox switch.** `useSandbox` (`src/lib/sandbox.tsx`) is the one reader of the `sandbox` query — a plain query, since the answer is fixed for the sidecar's life — and answers `available` as `true`, `false` or undefined, before it answers and after a failure, with `failed` and `retry` as `useModels` has them. `OpenChat` calls it, asks again once per live watch (`useAskAgainWhenLive`), and hands the composer `sandboxAvailable` and the chat's `sandboxDisabled` off the list watch. **A send says which switch its sender saw**: `chatSend`'s `sandboxDisabled` is the chat's switch as the list watch has it, `false` for a chat that has not started, and the sidecar refuses one that differs from the row with `KSTACK_CHAT_SANDBOX_CHANGED`, whichever window switched it. So the composer's Send and the transcript's Ask again wait for the list to deliver the chat, and a held send's Retry sends the switch it left with. From a switch's press until the list watch shows the value its mutation committed they also hold off (`switching`, from `useSandboxSwitch(chatID, watched)` in `src/lib/sandbox-switch.tsx`), since the mutation's answer can beat the watch's frame and a send between them would pass the old value; `SandboxSwitchProvider` holds that per chat at `AppLayout`, beside the outbox, so a pane that remounts while the mutation is in flight still waits, while a committed wait goes with the pane that started it, since a pane mounting later opens a watch whose snapshot already holds the commit. The composer mounts **`SandboxSwitch`** left of the model select, for an open chat on a machine with a sandbox alone: *Sandboxed*, or *Outside the sandbox* once switched, drawn disabled as *Sandboxed* until the list delivers the chat, and disabled while `switching`. `NewChatPane` draws none: a chat starts sandboxed. Turning it on opens a confirm `Dialog` that says what it means, and only its confirm calls `chatSandboxDisabledSet(id, true)`; turning it off calls `chatSandboxDisabledSet(id, false)` at once, since narrowing needs no warning. It draws the watch's value, never its own.

`ChatTranscript` (`chat-transcript.tsx`) draws **every answer that has something to say about itself**: status from the row, text from the blocks. `Streaming`/`Failed`/`Cancelled` always draw — a provider that refuses before its first chunk leaves an empty `Failed` row whose `error` is all there is — a `Complete` one with text, or, with none, **as the reason it stopped** (`Stopped: max_tokens`), since with a real provider that row is an answer its cap cut off while it was still reasoning. **`Stopped: tool_use` and `Stopped: pause_turn` draw under a `Complete` row whether or not it has text**: the first means the turn spent its tool budget and asked again, the second that a reply the provider paused mid-search was left there, out of resumes or out of searches, and the text such a row's earlier rounds hold ("Let me check the other namespaces") would otherwise read as the answer; every other reason keeps the no-text rule. It **labels an answer whose model differs from the one before it**, by the catalog's display name or the stored id when the catalog no longer has it, so a switch is visible where it happened and a chat that stayed on one model — the first answer included — is unlabelled. It takes the chat's `mode` and cluster, which is what `askAgain` needs. **An answer's thinking summary is a disclosure above its text**, labelled Thinking, drawn from the message's `thinking` field (the sidecar reads it off the blocks, so the webview never learns a provider's shape) and absent when empty. Untouched it follows the answer — open while the message is `Streaming` with no text, the pause it exists to fill, and closed from the moment text arrives, through completion; a click pins the reader's choice for that message for as long as the pane is mounted, and only another click changes it. The pin is the disclosure's own state (`Message` is keyed by message id), never persisted, so a remount starts from the rule again — closed, for a settled answer. The `<details>`' `open` attribute is React's alone: the summary's click handler prevents the native toggle and sets the pin. The summary is the model's text, so it goes through `Markdown` like the answer. An answer's text is markdown, drawn by **`Markdown`** (`markdown.tsx`): `react-markdown` + `remark-gfm` rendering to React elements, so there is never an HTML string to sink. A fence naming a language is highlighted by its `Code` component through **`src/lib/highlight.ts`** — every highlight.js grammar is available and none is in the main bundle: `import.meta.glob` makes each its own chunk, fetched from the bundle the first time a fence names it (the block is plain until it arrives), with `lowlight` producing a hast tree that `hast-util-to-jsx-runtime` renders to elements. Token colors are `markdown.css`. A fence naming no language is left plain, never guessed at, and `ALIASES` there is how a fence's word (`sh`, `yml`, `ts`) finds its grammar's file before the grammar can say so itself — raw HTML in an answer stays the literal characters, and a link is drawn with its URL as `title` but no `href`, since the webview has nowhere to open one. The sidecar's system prompt (`chatsvc/prompts/system.md`) asks for GitHub-flavored markdown and no HTML, so what is asked for and what is rendered agree. **An answer that searched or cites draws two more things under its text**: *Sources*, always visible, one item per cited URL — the title, the host beside it, the whole URL as the item's `title` since nothing in the webview opens one — and *Searched the web · N*, a closed disclosure holding the queries as plain text, drawn as soon as they are seen (the provider's row is in the live list the moment the stream shows its call, so while the answer streams, and under one that failed or was cancelled), since they are what left the machine. A question stays plain text in `whitespace-pre-wrap`. **A question's context — the cluster card, then the memory notes, then the chat's workspace, then, on a machine with a sandbox, where its commands run — is a closed disclosure above it**, labelled *Context*, drawn as plain text like the question itself and never markdown, since its names came from the cluster — it is how the user sees what the provider was told, at the message it rode. The transcript follows a growing answer only for a reader within 32px of the end.

`ChatNav` (`components/widgets/chat-nav.tsx`) is the recent list, and takes `mode`. The mode decides two things at once, which is why it is one prop: **which chats it lists** (the spinner still gates on the unfiltered phase, "No chats yet." on what is left) and **where a row points** — `/chat/$chatId` in chat mode, the panel's `chat` search param on the dashboard, where "New chat" is not rendered at all. **No dashboard row is ever marked active**, and none needs to be: the panel shows the list or the open chat, never both. In chat mode it is the sidebar's nav, the way `DashboardResourceNav` is on the dashboard; rename edits in place, delete confirms in a local `Dialog` (the app-wide `DialogProvider` names window-level dialogs and carries no payload to say *which* chat). A row whose chat has a request waiting on the user (`Chat.awaitingApproval`) draws a dot labelled *Waiting on you*, since an agent can wait in a chat the user is not looking at.

**`DashboardChat`** (`dashboard-chat.tsx`) is what the dashboard's right sidebar holds. Which chat it is on is the `chat` search param — window state, so every window's panel can be on a different one. Nothing selected is `NewChatPane` with `ChatNav` in its `empty` slot (typing is how a chat starts here, so there is no "New chat" button); a chat selected is `ChatPane` under a "Chats" button. → [ADR: the answer is a record](docs/adr/2026-09-10-the-answer-is-a-record.md).

### Theming & window frame

**Browser-storage keys are `kstack:`-prefixed and kebab-case** — `kstack:sidebar-width`, `kstack:sidebar-open`, `kstack:right-sidebar-width:<mode>`, `kstack:right-sidebar-open:<mode>`, `kstack:history-forward-ceiling`. The prefix marks the app's own keys apart from anything `@kubetail/ui` persists (it writes an unprefixed `sidebar_state` cookie), and one shape keeps them greppable. **`storageKey` (`src/lib/storage-key.ts`) forms every one of them** — the two persistence hooks call it, and so does `history-nav.tsx`, the one key not behind a hook. Call sites pass the name alone, never the prefix. What belongs there is the shape of the chrome (a pane's width, whether it is open) and a history ceiling; a *setting* — one the user picks in the Settings dialog — goes to the host's `host.json` instead.

**Every window shares one `localStorage`, and each has its own `sessionStorage`.** So the chrome's shape (`usePersistedWidth`, `usePersistedFlag`) is an app-wide default written on every drag and toggle, with no live sync: resizing one window leaves the others alone, and the next window opens the way the last one was left. This is deliberate — the sidebars belong to the window's chrome, not to what it is looking at, and tabs will be webviews of their own, so a per-webview width would have two tabs of one window disagreeing about the sidebar. The history ceiling is the opposite case and lives in `sessionStorage`: it describes one webview's own history stack.

Two axes in `src/lib/theme.tsx`: **color scheme** (`system`/`light`/`dark` → `.dark` class on `<html>`; Tailwind `dark:` variant) and **theme/skin** (reserved, not built). The preference persists in the host's `host.json` — **no localStorage**; `src/lib/host-file.ts` owns the read/update/subscribe protocol. Boot is synchronous via `window.__KSTACK_HOST__` + the inline script in `index.html` (hand-mirrors `resolveColorScheme` — keep in sync); its inline `<style>` likewise hand-mirrors the boot mark's four tokens (`--primary`/`--primary-foreground`, light and dark) from `index.css`, and the root `index.test.ts` pins them. Changes write through and broadcast to all windows. → [ADR: host.json settings](docs/adr/2026-08-09-host-json-settings.md), [ADR: first-paint theming](docs/adr/2026-08-09-first-paint-theming.md). The Settings dialog hosts the picker (`settings-dialog.tsx`), opened from the app bar's settings button.

Window frame is per-platform (macOS native / Windows frameless-opaque / Linux frameless-transparent): `WindowFrame` (`window-frame.tsx`, wraps the app at `__root.tsx`) paints Linux's border/shadow and is a passthrough elsewhere; `WindowResizeHandles` is its **sibling**, never a child (the frame's `contain: paint` would clip it). `main.tsx` tags `<html class="frameless">` on Linux only. **Full-height screens use `min-h-[var(--app-min-h)]`, never `min-h-svh`** — the frame insets the app on Linux (`app-layout.tsx` displaces the library's hardcoded `min-h-svh` with `min-h-0`). Maximized Linux collapses to full-bleed (`useWindowMaximized`). → [ADR: per-platform window chrome](docs/adr/2026-08-09-per-platform-window-chrome.md).

Off macOS there's no native menu bar: `AppMenu` (`app-menu.tsx`) is the hamburger at the left of the app bar (`app-bar.tsx`), owns `Ctrl/Cmd+N`/`Ctrl/Cmd+Q`, and invokes the `new_window`/`quit` commands; `WindowControls` (`window-controls.tsx`) supplies caption buttons.

### GraphQL — never talks HTTP directly

The webview has **no network access**. urql routes everything through Tauri IPC (`src/lib/graphql/`): queries/mutations via `invoke('graphql_query')` (`invoke-fetch.ts`), subscriptions via `invoke('graphql_subscribe'/'graphql_unsubscribe')` over a Tauri `Channel` (`subscribe-exchange.ts`, own capped-backoff reconnect). → [ADR: GraphQL over Tauri IPC](docs/adr/2026-08-09-graphql-over-tauri-ipc.md). Read `src/lib/graphql/client.ts` and its tests before touching transport/retry logic.

A `next` frame marked **`extensions.watchFailed`** is the sidecar naming the reason a watch died (its `WatchFailureExtension`). `subscribe-exchange` routes it down the ordinary drop path — report, hold last-known data, reconnect — and never to the urql sink: urql merges each frame into the previous result, so an errors-only frame pushed to the sink would re-deliver the last frame's data and fold it twice. **Key on the marker, never on shape** — a non-null field erroring nulls its parent, so a live frame with a field error looks identical, and tearing the subscription down for one would turn a bad field into a reconnect loop. → [ADR: watch-failure reporting](docs/adr/2026-08-14-watch-failure-reporting.md).

Connection lifecycle is published out of band on the per-operation **transport-status registry** (`transport-status.ts`): `connected` + a process-wide monotonic `generation`, bumped on the host's **`open` frame** — deliberately *not* on the `graphql_subscribe` ack (the host acks before it dials; an ack-keyed reset would clear last-known data on every failed retry during an outage). Consumers use **`useWatchSubscription`** (`use-watch-subscription.ts`), never raw `useSubscription`; it generation-gates its accumulator so state from a previous connection never survives a reconnect. urql keys an operation on query + variables alone, so two consumers of one watch share a connection — and a consumer that mounts into a stream already running never sees the snapshot that opened it. **`unshared: true`** gives an instance its own connection, at the cost of a second cold list; set it where a watch has more than one consumer and one of them can mount late (`useClusterCachedDataKinds`, whose sidebar consumer unmounts on collapse). `watchPhase(synced, connected)` turns the delta watches' `Bookmark` into the three states a view renders — `connecting` (no complete snapshot yet, whatever the transport is doing), `live`, `reconnecting`. → [ADR: transport-status generation](docs/adr/2026-08-09-transport-status-generation.md).

**Frames are reduced as a batch, once per animation frame.** A snapshot arrives one frame per object, each its own IPC task, so `useWatchSubscription` queues them and calls the reducer once per `requestAnimationFrame` — or after 250ms, whichever comes first, since a minimized window gets no frames and the queue would otherwise grow until it came back — with `frames: Data[]` (never empty), publishing the result through `useSyncExternalStore` — one render, one map copy and one sort per flush, whatever the burst. A map-accumulating reducer copies its map once per batch and applies each frame in place (`applyChange` mutates); a cheap per-frame fold (last value, append) is lifted with `perFrame(step)`. A frame from a newer connection drops the pending batch. In tests, a suite that pushes a frame and asserts on the next line calls `flushWatchesSynchronously()` from `@/test-utils` at module scope; the batching itself is covered in `use-watch-subscription.test.tsx` with a manual scheduler. → [ADR: batch per animation frame](docs/adr/2026-08-30-batch-watch-frames-per-animation-frame.md).

### Tests

Vitest + `@testing-library/react` (jsdom), co-located (`*.test.ts[x]`). Mock the Tauri bridge with **`mockTauriCore()` from `@/test-utils`** (+ `vi.mock('@tauri-apps/api/core', …)` and dynamic import of the module under test). ### Lint / build

- `pnpm lint` (ESLint: airbnb-extended, then `oxfmt --check`) → `make lint-js`. Run before
  committing. Formatting is part of `lint` here, matching `lint-go`'s `gofmt -l` and `lint-rust`'s
  `cargo fmt --check`. `pnpm format` writes.
- **Formatting is oxfmt, configured in `.oxfmtrc.json`.** Its output matches prettier's, so
  `eslint-config-prettier` stays — it is the list of stylistic rules airbnb would otherwise use to
  argue with the formatter. Scope is set by the globs in the `lint`/`format` scripts, and a
  **directory argument mixed with a glob silently narrows to the glob's extensions** — the reason
  both scripts pass globs only. `.vscode/settings.json` runs the same binary on save through the
  `oxc.oxc-vscode` extension, which resolves it from `node_modules`, so the editor and CI agree on
  the version.
- The **React compiler** is on in two places that must stay in step: the Vite/babel transform
  (`vite.config.ts`) and its lint rules, which ship inside `eslint-plugin-react-hooks` — there is no
  separate compiler plugin to install. `eslint.config.ts` applies the plugin's `recommended-latest`
  on top of airbnb's narrower set. So a bail-out the transform would take silently is a lint error
  instead: mutating a prop, reading a ref in render, `setState` during render.
- **Write as though the compiler weren't there.** It is a speed-up, not a correctness guarantee —
  it bails per-function, silently. So `react-hooks/exhaustive-deps` is an **error**, and manual
  `useMemo`/`useCallback` are ordinary tools, not smells: the compiler rules never discourage them
  (`preserve-manual-memoization` exists to protect one). `void-use-memo` flags only a `useMemo`
  returning nothing — a `useEffect` written as a memo.
- `pnpm build` = `tsc -b && vite build`. Dev: `pnpm dev` (webview) or `pnpm tauri dev` (full app).
